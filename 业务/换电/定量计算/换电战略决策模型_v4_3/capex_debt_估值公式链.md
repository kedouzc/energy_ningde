> 定义、是个混杂量"。

## 0. 两种方法的骨架，和它们的交汇点

```
方法 M（相对可比法 / 倍数法）：
    宁德归属价值 = ( EBITDA × 倍数18×  −  Debt_M ) × 40%持股
                    └──产出侧──┘        └来源侧┘

方法 D（绝对内在价值法 / DCF）：
    宁德归属价值 = ( FCFF÷CRF ＋ 期末残值PV  −  Debt_D ) × 40%持股
                    └────产出侧────┘        └来源侧┘
```

**两个方法唯一的公共变量是 Debt——这正是本次审核的全部焦点。** 
产出侧（EBITDA/EV、FCFF/EV_crf）两个方法各自独立、互不相干；
只有"扣掉多少债"这一步，两条线本该用同一个数（因为问的是同一件事：
"2030 年这个时点，这门生意欠了多少钱"），但**代码里现在是三个不同的数**（第 3 节）。

## 1. 方法 M（倍数法）全链条

按池计算（`business.py::build_swap_business`），四个池各自独立，最后加总。以下以单池
`pk` 为例，公式对每个池都成立。

| 层 | 中文含义 | 程序变量 | 公式 | 时点 |
|---|---|---|---|---|
| L1 | 稳态年 EBITDA | `pool_ops[pk].ebitda_yi` | `revenue − opex`（收入减运营成本，不含折旧） | **{2030}**（用 2030 车队规模、2030 电价算的收入成本） |
| L2 | 企业价值 | `pool_ops[pk].enterprise_value_yi` | `ebitda × finance.swap_ev_ebitda`（18×，`base.toml`拍值） | **{2030}**（把 2030 年这一年的现金流能力，按市场倍数资本化——隐含"这个能力会持续下去"，下面第5节会点出这一步的一个未言明假设） |
| L3 | **债务（当前口径）** | 局部变量 `debt_by_pool[pk]`（business.py:331，不直接暴露为独立字段） | `lifecycle_by_pool[pk] × finance.debt_ratio`（60%） | **`{?}` 不是任何单一时点**（下面详解） |
| L4 | 项目权益价值 | `pool_ops[pk].project_equity_value_yi` | `max(0, ev − debt_by_pool[pk])` | 跟随 L3，不干净 |
| L5 | CATL归属（单池） | `pool_ops[pk].catl_value_yi` | `equity_value × finance.construction_ownership`（40%） | 跟随 L4 |
| — | **CATL归属（汇总，报告headline）** | `swap_business.catl_attributable_value_yi` | Σ_池 `catl_value_yi` | **= 5,091.6 亿**（中枢） |

**L3 是问题所在**：`lifecycle_by_pool[pk]` 即 `capex.lifecycle_capital_base_by_pool`，
它的定义是"**每个电池批次（cohort）按自己的装机年份为 t=0、折算 15 年全周期现金流的
现值，再把所有批次直接加总**"（`capex.py::build_capex` 第356-443行的 cohort 循环）。
2026 年装的批次以 2026 为 t=0，2030 年装的批次以 2030 为 t=0——**这是一个横跨多个
不同基准年的存量加总，不对应任何单一年份的"账上还欠多少钱"**。它的本职是给 EAC/门槛
用的（`× CRF` 得年度资本要求），不是给"2030 年这一刻的负债余额"用的。

来自 `business.py::_dcf_cross_check`（第188-246行），先算总量层（不分池，用汇总

|---|---|---|---|---|

## 4. debt 正确应该怎么算，为什么，公式怎么写

**先问本质（这是 `capex诊断.md` 原则一，我认同这条原则）**：两个估值方法最后都要问
"2030 年这一刻，扣掉的这笔债，对应的是哪笔钱？"——答案只能是"**到 2030 年为止，
已经实际花出去、还没被更新掉的那部分资产，当初有 60% 是借的**"。这既不是 A（含
2030 年以后才发生的更新支出），也不是 B（用现值折算、混进了时间价值，而债务本金
不该有时间价值——下面会证明这点）。

**正确公式（cohort 逐批算，`capex诊断.md` §4.2 的思路，我验证过是对的且代码里
已有现成的钩子）**：

对每个电池 cohort（`capex.py::_cohort_generations` 已经在算的那个循环，供折旧用）：

```
k = floor((2030 − install_year) / life)                    # 2030年是第几代在役
在役成本_c = initial_capex_c × price(install_year+k×life) / price(install_year)
```

这一步**不是新逻辑**——`capex.py` 第376-379行：

```python
elapsed_to_target = max(0.0, float(target_year) - install_year_f)
in_service = generations[min(int(elapsed_to_target // life), len(generations) - 1)]
```

这个 `in_service` 变量本身就是"2030年在役的那一代"，`in_service["cost"]` 就是
"在役成本"——**这行代码现在只用来算折旧，没有用来算债务，改动只是多读一个已经
算好的数、按 `battery_pool` 汇总、乘 60%**：

```
D_by_pool(2030) = Σ_{cohort ∈ pool} in_service["cost"] × 0.6
```

**这一步天然落在 2030（in_service 就是按 target_year=2030 选出来的那一代），
不需要任何时点转换、不涉及折现率选择、没有第5节要讨论的那类争议。**

**两个方法该不该用同一个 `D_by_pool(2030)`？——应该，而且这正是解决第3节"三个
debt互不相同"的办法：** 方法 M 和方法 D 现在的 `debt_by_pool` / `dcf_valuation_debt_yi`
两处都应该**换成**这同一个新算出的 `D_by_pool(2030)`（分池版给方法M，加总版给方法D）。
统一之后，第3节的A、B、C三个数字自然合并成一个。

## 5.（关键）时点处理本身：我要纠正 `capex诊断.md` 的一处数学错误

`capex诊断.md` 的**原则七**说："复合现金流不能用统一因子折算……正确做法：逐笔重算。"
并据此**撤回**了一个此前算出的结论（"NPV 修正后 88.1 亿"）。

**我核对下来，原则七这个说法在数学上不成立**——这也是为什么我说你"不敢信"
`capex诊断.md` 是有道理的，它在这一点上确实站不住。以下是完整证明，你不需要懂
编程，只需要会算指数。

### 5.1 一个可以自己验证的代数事实

一组现金流 `{CF_t}`，**全部按同一个固定利率 r 折现**，它在基准年 B 的现值总额
`V(B) = Σ_t CF_t / (1+r)^(t−B)`。现在把基准年从 B1 换成 B2：

```
1/(1+r)^(t−B2) = 1/(1+r)^(t−B1) × (1+r)^(B1−B2)
```

两边同乘 CF_t 再对 t 求和：

```
V(B2) = V(B1) × (1+r)^(B1−B2)
```

**这对任何现金流分布都精确成立**——不是近似，是"先折现每一笔再加总"和"把加总后
的数整体乘一个系数"，本来就是同一个算式的两种写法（乘法对加法的分配律）。
`valuation_capital_pv`（D4）和 `terminal_residual_pv`（D3）都是"用同一个 `wacc`
折现出来的现值总额"（我核对过 `capex.py` 代码，两处循环里 `wacc` 都是单一常数，
没有变化），完全满足这条代数事实的前提。

### 5.2 原则七的例子错在哪

`capex诊断.md` 列了这张表：

| 现金流 | 折到2026 | 移到2030的因子 |
|---|---|---|
| 2026年支出 | 原值 | ×1.075⁴ |
| 2045年支出 | ÷1.075¹⁹ | ÷1.075¹⁵ |

它拿"折到2026的因子"和"移到2030的因子"这两个**不同的数**去比，发现不一样，
就下结论"因子互不相同、不能统一折算"。但真正该看的是"**同一笔钱，从2026-口径
换算到2030-口径，要乘的那个比值**"：

```
2026年支出：(移到2030的因子) ÷ (折到2026的因子) = 1.075⁴ ÷ 1       = 1.075⁴
2045年支出：(移到2030的因子) ÷ (折到2026的因子) = (1/1.075¹⁵) ÷ (1/1.075¹⁹) = 1.075⁴
```

**两笔现金流的换算比值完全相同，都是 1.075⁴。** 这张表本身没有算错任何一个数字，
只是拿错了要比较的两列。

### 5.3 代入实际数字，验证撤回的那个结论是否站得住

`D4`（valuation_capital_pv, 2026口径）= 3,725.0亿，`D3`（terminal_residual_pv,
2026口径, 已税后）= 179.6亿，都可以精确移到2030：

```
1.075⁴ = 1.335469
D4 @2030 = 3,725.0 × 1.335469 ≈ 4,974.6 亿
D3 @2030 = 179.6 × 1.335469 ≈ 239.9 亿
```

代入 D6 公式（NPV，不含debt）：

```
NPV @2030 = D2 + D3@2030 − D4@2030 = 4,822.8 + 239.9 − 4,974.6 ≈ 88.1 亿
```

**这精确对上了 `capex诊断.md` 自己说"此前算出、后来撤回"的 88.1 亿**（反算2026
口径：88.1÷1.335469≈66.0，也对上文档提到的"66.0"）。也就是说：**被撤回的那个
计算，用的正是我刚证明为精确成立的方法，撤回的理由（"统一因子不成立"）本身是
错的，88.1 这个数很可能一直是对的。**

> ⚠️ **不要把这个结论和"debt能不能这样移"搞混**：原则六（债务不可复利）**是对的**——
> D5/B（负债本金）不是"用固定利率折现出来的现值总额"，它是一个契约余额，不满足
> 5.1 的前提，所以**不能**用同样的方法搬到 2030。第3-4节已经给出 debt 该怎么算的
> 正确方法（cohort 法），跟这里的代数无关。**原则七的错误，只影响 D3/D4 这类"现值
> 总额"的搬家方式，不影响 debt。**

### 5.4 P5（原则七里挂着的那个"待拍板"问题）其实已经有答案

`capex诊断.md` 把"逐笔重算用 7.5%(WACC) 还是 12.4%(CRF隐含)"列为待拍板的 P5。
**答案是 WACC**——因为 D3、D4 这两个量本来就是用 `wacc` 算出来的（`capex.py`
代码里没有任何一处用 CRF 折现资本或残值），要把"同一个量"搬到别的基准年，必须
用"造出它的那个利率"，换一个利率就不是"移动"，是"重新定义"了。这不是我拍的，
是 5.1 的代数直接决定的——用 WACC 才能保证 V(2030)=V(2026)×(1+WACC)⁴ 这个等式
成立；换成 CRF 的话，等式根本不成立，因为 D3/D4 从一开始就不是按 CRF 折出来的。

## 7. 修正后的最终公式，和"现在能不能给数字"

```
方法 M（倍数法）：
    CATL归属_M = Σ_池[ max(0, EBITDA_池×18 − D_by_pool(2030)) ] × 40%
    —— D_by_pool(2030) 需要新代码（第4节），其余已有

方法 D（DCF）：
    NPV @2030        = ev_crf ＋ 179.6×1.075⁴ − 3,725.0×1.075⁴  ≈ 88.1亿   ← 现在就能给，见5.3
    CATL归属_D @2030  = max(0, ev_crf ＋ 239.9 − D_2030(汇总)) × 40%
    —— D_2030(汇总) 同样需要第4节的新代码，其余（ev_crf、残值PV移到2030）已经算完
```

**结论**：这条链上，唯一真正需要写新代码的，是第4节的 debt cohort 算法（一个
字段，改动不超过20行，且复用了已有的 `in_service` 计算）。时点转换本身（残值PV、
资本PV移到2030）不需要新代码，是精确的代数运算，已经在第5.3节用现有的、已公开
的数字验证过。`capex诊断.md` 因为原则七的错误，把这部分也划进了"必须等代码"，
这是过度保守。

> 框架，不是就着代码找补。

## 问题1+2（合并回答）：稳态债务要不要考虑未来更新，debt_M/D 该不该共用

**结论：不要考虑未来更新；M 和 D 必须用同一个数。**

**为什么**——这是"企业价值桥接到股权价值"（`Equity = EV − Debt`）这个动作的
定义本身决定的，跟你用哪种方法算 EV（倍数法还是DCF）无关：

`Debt` 在这个桥接公式里，问的永远是**资产负债表上的一个快照问题**——
"截至估值这一刻，账上实际欠了多少钱"。它不是一个预测量，是一个记账量。

> **类比**：你看一家真实上市公司的股价，用的公式是 `市值 = EV − 净负债`，
> 这里的"净负债"是**这一刻资产负债表上的数**，不是"未来十年还要借多少钱的预测"。
> 未来要不要再借钱、借多少，属于**未来的融资决策**，那笔钱进未来的现金流（会拉低
> 或不影响未来FCFF，取决于怎么花），**不会倒着影响今天的负债余额**。

如果把"未来更新还要借的钱"也算进今天的 debt，会犯**双重扣减**的错误：
一次是未来更新支出本身会（如果建模正确）拉低未来现金流、从而拉低 EV；
再算一次"未来要借的钱"去扣减今天的股权价值，等于把同一笔负担扣了两次。

**M 和 D 该不该共用同一个 debt？——该，而且没有第二个正确答案。** 两个方法在
"债务是什么"这件事上问的是**完全同一个问题**（截至2030年，账上欠多少钱），
只是产出侧（EV怎么算）用了不同框架。产出侧可以不同、债务侧不能不同——
这正是 `capex诊断.md` §4.2 那个 cohort 算法（"2030年在役那一代的成本×60%"）
该被两条线**同时**采用的原因，不是巧合，是这件事的本质决定的。

## 问题3：CRF 倒算出的 ev_D_2030，是否已经包含 residual，再加会不会重复算

**先给一个干净、确定的答案，再告诉你这个问题底下还藏着一个更大的问题。**

### 3.1 干净的答案：不会重复，因为 CRF 数学上假设终值=0

`CRF(i,n) = i ÷ (1−(1+i)⁻ⁿ)` 这个系数，本质就是"**等额还本付息贷款**"的还款系数——
一笔本金，按利率 i、分 n 年等额还清，每年还多少。这类贷款的定义就是：
**还到第 n 年，本金正好还完，一分不剩**。所以 `forward_fcff ÷ CRF` 这个算法，
数学上等价于说："如果这门生意未来15年每年产出 forward_fcff 这么多钱，
第15年末（2045年）这门生意（作为一个整体）**价值归零**"。

`residual_2030` 这一项，加的是"第15年末**这批还在服役的电池本身**还能卖多少钱"——
这跟"CRF公式假设的'生意整体归零'"是两件不同的事：CRF 那一步已经承诺了"归零"，
`residual` 是在说"不对，电池本身还没归零，还值一点钱，补回来"。**这一步不是
重复计算，是纠正 CRF 公式过度悲观的一个假设**（它假设生意在2045年一文不值，
这明显不对，因为电池还能卖，所以补回来是对的）。

### 3.2 但这个问题底下还藏着一个更大、更值得你在意的问题

**我在回答你这个问题的过程中，顺带做了一次粗略核算，结果让我意识到
`forward_fcff` 这个数本身可能有问题——比 residual 这个疑点更值钱，你问对了方向。**

`forward_fcff = EBITDA×(1−税率) + 折旧×税率`，我把这个公式拆开算：

```
= EBITDA − EBITDA×税率 + 折旧×税率
= EBITDA − 税率×(EBITDA − 折旧)
= EBITDA − 税率×EBIT
= (EBITDA − 税) = 税后息前折旧前利润 − 税额
```

代进中枢数字（EBITDA 850.4、折旧342.4、EBIT 508.0、税率25%）：
`forward_fcff = 850.4×0.75 + 342.4×0.25 = 637.8+85.6 = 723.4` ——
跟框架提案页面里"forward FCFF 723.4亿"这个数完全对上，验证了我拆解得对。

**问题在这里**：这个公式里**没有任何一处减掉"实际要花的更新电池的钱"**。
标准的自由现金流公式应该是：

```
真实FCFF = EBIT×(1−税率) + 折旧 − 资本性支出（含更新）
```

而这个模型的 `forward_fcff` 只做到 `EBIT×(1−税率) + 折旧`，**减号后面那一项
"−资本性支出"整个是缺的**。它的设计初衷（见 `换电毛估估_v3.2.md §1.2.3`）是——
"折旧只作税盾桥接，重置已经被 CRF 年金化内含，不能再减一次"，意思是"更新的钱
不在这条现金流里明着扣，而是靠**除以 CRF**这个动作暗中体现"。

**这个"暗中体现"是否真的成立，我核算了一下，量级对不上：**

如果按"稳态下，每年更新支出大致等于折旧"这个通行近似（工程经济学里常用的
"维护性资本支出≈折旧"），那真实FCFF应该更接近：

```
真实FCFF(近似) ≈ EBIT×(1−税率) = 508.0×0.75 = 381.0亿
```

这比 `forward_fcff`（723.4亿）**少了整整一个折旧的量级（342.4亿）**。如果用
这个更小的数去算价值（哪怕用同样的12.4%期望回报率折成永续或15年年金），
算出来的企业价值会比现在的 `ev_crf`（4,822.8亿）**明显更低**（我粗算大概在
2,500—3,900亿区间，取决于用永续还是15年期，这个区间本身还不精确，
下面会说为什么不精确、以及怎么精确地把它算出来）。

> ⚠️ **这不是我给你一个新的"高估多少"的结论——我在犯 `capex诊断.md`
> 犯过的错（原则八说的"代码没跑，别下量化结论"），我不会重复那个错误。
> 这里只负责说清楚"这个近似（折旧≈更新支出）本身对不对，我不确定，需要用
> 模型里已经算好的真实数据去验证，不能靠拍"，把这件事的分量讲清楚，
> 不给一个我自己都不确定精度的数字。**

**为什么"折旧≈更新支出"这个近似本身也不一定对**：电池是**降价的**——
每一代更新买的新电池比上一代便宜（`replacement_pv`的计算已经算过这个价格路径）。
折旧是按"历史买入价"分摊的，更新支出是按"当时的新价"发生的，两者不严格相等，
方向和大小都需要实际算过才知道。

**好消息：不需要凭空猜，模型里已经有算好的真实数据可以直接验证**——
`capex.py` 的 `replacement_net[year]` 这个字典，已经逐年算出了"这一年实际要花
多少钱更新电池"（扣掉卖旧电池回收的钱），这正是 `valuation_capital_pv` 用来
折现的那批现金流。**把 2031—2045 年这些真实的更新支出，接进一个标准DCF
（EBIT×(1−税)+折旧−真实更新支出，按WACC折现），跟现在走"CRF捷径"算出的
`ev_crf` 对比一下差多少——这是一个可以直接跑代码验证的动作，不需要再猜。**

### 3.3 这件事和 CRF 这个工具本身的定位有关，值得说清楚

CRF 在这个模型里，从一开始就是被设计来做**一件不同的事**："算门槛"——
拿全周期投资（含未来更新，`capital_multiplier` 里已经包含）乘以 CRF，
反推"这门生意每年至少要挣多少钱才配得上这笔投资"，这是一个**及格线测试**，
不是一个**估值工具**。`_dcf_cross_check` 把它反过来用（拿实际赚的钱除以CRF，
倒推一个"企业价值"），是在**借用及格线测试的除数，去做原本该用真实现金流
DCF做的事**。这两件事用同一个除数，未必天然等价——3.2 的粗算显示可能确实
不等价，且差距不小。

**这跟 T1（18×合不合理）的关系**：现在的"隐含倍数5.67×"（=ev_crf÷EBITDA）
本身可能就因为这个原因被高估了。如果按标准DCF重算出的企业价值更接近
2,500—3,900亿区间（**未验证，仅供感知量级**），隐含倍数会掉到3×附近，
跟18×的差距（也就是第5章"押注"的部分）反而会**更大**，不是更小。
这件事应该在写第5章之前，用代码把真实数字跑出来，正式列进"待拍板"清单，
建议编号 **P7**。

## 关于 `lifecycle_capital_base`：你的怀疑是对的，它本身确实不是一个干净的量

你说得对，我需要更精确地讲清楚，之前"本职是给EAC用"这个说法讲得不够透。

`lifecycle_capital_base = Σ_cohort (每个批次自己的PV，各自锚在自己的装机年)`。
它**不是**名义总值（它是折现过的），**也不是**任何单一日期的现值（每个批次
折现的起点不一样，加总后不对应任何一个具体的年份）。**它是一个夹在中间、
本身不完整的量——只有再乘一次 CRF、变成"Σ各批次自己的年金"之后，才重新变成
一个有清晰含义的东西**（因为乘法对加法满足分配律：`(Σ PV_c)×CRF = Σ(PV_c×CRF)`，
后者是"同一年份里几笔不同来源的年金相加"，这是站得住的，前提是这个乘法必须
做完才能用，中间那个"没乘CRF"的和数本身不该被读成任何独立的经济含义）。

**这直接回答你说的"值不值——获得是投入的几倍"该用哪个数**：**不该用
`lifecycle_capital_base`（4,297.3），该用 `valuation_capital_pv`（3,725.0，
干净的、单一基准年2026的现值）作为"投入"这一侧，跟同样折到2026（或统一折到
2030后）的"值多少"相除。** 这也是 `capex诊断.md` §5.4 里提的 `lifecycle_capital_pv_B`
（把每个批次重新折回同一个基准年B再相加）真正该补的地方——补了之后，它会是一个
干净的现值，可以放心拿来做"投入产出倍数"，而现在的 `lifecycle_capital_base`
不行。

## 关于泛化：这套问题是不是"持续更新型重资产"的通用核心算法

**认同，而且我可以说得更具体一点，帮你判断值不值得现在就投入沉淀。**

这次暴露出来的坑，可以收敛成三条**跟CATL换电这个具体案例无关**的通用规则：

1. **Debt 是资产负债表快照，不是现金流预测**——EV减债务这一步，债务永远取
   "估值这一刻实际欠多少"，不管未来还要投多少钱、未来现金流怎么算，这条对
   任何"持续更新型重资产"（数据中心、储能电站、租赁车队、连锁设备）都成立。
2. **工程经济学的"及格线/EAC捷径"和"真实自由现金流DCF"是两套不同的框架，
   不能互相借用除数**——EAC/CRF天生是用来做"这笔投资划不划算"的及格线测试，
   把它的除数直接拿去给"实际现金流"做资本化，会不知不觉漏掉真实的资本性支出。
   这个坑对任何"用EAC思路起步、后来想升级成DCF"的模型都成立。
3. **移动一个量的时点前，先问它是"用固定利率折现出来的现值"还是"契约余额/
   记账量"**——前者可以精确用统一因子搬（第5节已证明），后者不能，需要
   直接在目标时点重新算出来。这条对任何多时点估值模型都成立。

## 第三轮：NPV转负之后，权益价值1,341.5亿是怎么来的（2026-09-04，代码已实跑验证）

`dcf_npv_true_yi = −54.9亿`（WACC 7.5%折现），代入实际代码用二分法反解：
**NPV_true = 0 出现在 WACC ≈ 7.31%**——也就是说，这门生意剥离资本结构后的
真实无杠杆回报率约 **7.31%**，比WACC低了约19个基点，量级上几乎持平，
不是明显跑输，也不是明显跑赢。**这一步是实跑代码算出来的，不是估的。**

**但同一时刻，`dcf_catl_value_true_yi`（CATL归属，扣完debt后）是正的1,341.5亿**——
这不矛盾，是**杠杆放大**（leverage amplification），不是"套利"（arbitrage，
无风险利差）：

- `WACC(7.5%)` 本身是"便宜的debt成本(2.5%)"和"贵的股权要求回报(Ke≈15.9%，
  见第一轮§1推导)"两者的加权混合——debt优先受偿、拿固定的低成本，equity是
  剩余索取权。
- 这门生意的真实回报（≈7.31%）远够覆盖debt的2.5%，但远不够equity单独承担
  全部风险时所要求的15.9%——**如果equity要单独扛这门生意，它值不了这么多**；
  但debt先把风险最小的那一段拿走、equity只需要在40%这个更小的资本基数上
  拿剩余，把一个"勉强持平"的资产回报放大成了equity上一个看得过去的正数。
  这与按揭买房、杠杆收购放大股权回报是同一个机制。
- **这不是无风险的："放大"是双向的**——如果真实回报进一步跌破debt成本，
  equity价值会比资产价值跌得快得多（模型里`max(0,·)`这个下限就是这个风险
  的显性表达：equity可以被压到0）。`Ke=15.9%`远高于`WACC=7.5%`，正是市场
  对equity承担这份放大风险要求的补偿，不是equity凭空多赚的钱。
- **规模越大，equity绝对值越大**这句话本身没错（同样的利差乘更大的本金，
  总利润更大），但**规模越大不等于越安全**——利差收窄的风险按同样比例放大。

**这个发现比"押注部分4,155.1亿"更根本、更该写进第5章**：它说明CATL能拿到
1,341.5亿归属价值，**很大程度上取决于60%债务/2.5%利率这个杠杆假设是否成立**，
而不是这门生意本身有多好（无杠杆回报只是勉强持平WACC）。第5章如果只讲
"5.67×/5.5×隐含倍数 vs 18×拍定倍数"，会漏掉这一层——建议第5章额外加一句
"这1,341.5亿有多少是杠杆贡献的，不是资产本身挣的"。

**一个便宜的验证途径（暂未做，建议列为下一步可选项，对应`capex诊断.md`的T5）**：
如果直接用 `Ke≈15.9%` 折现股权现金流（框架L），算出的权益价值应该与这里
"EV−debt"算出的1,341.5亿接近（第一轮§1.2已证明：只要杠杆恒定，U与L应该
相等）。两者若接近，说明"稳态、恒定杠杆"这个假设内部自洽；若差很多，
说明杠杆假设（debt每年都精确维持在60%）本身有问题，需要重新审视。

**能不能现在就沉淀成 skill/模板 agent——我的判断是：还不能，但快了，缺一步。**

缺的这一步是：**上面这些结论目前还停留在"推导+粗算"，还没有拿真实代码把
"标准DCF vs CRF捷径"这两条线都跑出来、看实际差多少**（3.2节那个"未验证"）。
一个方法论 skill 的可信度，取决于它在至少一个真实案例里被**验证过**、不是
只被**推导过**——这正是这个项目自己在 `DECISIONS.md` 里反复吃过的亏（"此前
