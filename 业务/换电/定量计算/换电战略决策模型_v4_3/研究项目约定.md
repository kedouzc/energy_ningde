# 研究项目约定

> **这是一份「工作台设置」，不是一份研究方法。**
> 新开任何一个投资研究项目，把这份文件复制进新仓库根目录，人和 AI 都照着它做。
>
> **它和 skill 的区别，一句话：**
> **skill 管"这次做得对不对"，本文件管"下次还找得到吗"。**

---

## 0. 它和 skill 到底差在哪

| | **skill** | **项目约定（本文件）** |
|---|---|---|
| 是什么 | 一份**检查表／提问链**，AI 做某类任务时读 | 一套**文件与协作的规矩**，项目开工时铺好 |
| 什么时候起作用 | **做那件事的时候**（"现在要给倍数了，读一下"） | **一直起作用**（每次写文件、每次改动都在守它） |
| 决定什么 | **你怎么想**——想的顺序、不许跳的步骤 | **你想过的东西留不留得住** |
| 载体 | `.claude/skills/<name>/SKILL.md`，AI 按需调用 | 仓库里的一份 md ＋ 目录结构 |
| 怎么迁移 | 装一次，到处可用 | **复制到新项目的仓库里** |
| 失效时的症状 | **该想的没想到** | **想到了，但下次找不到了** |

**判据（分不清时用这条）：**

> **一条规矩，如果 AI 不专门读也应该遵守 → 项目约定。**
> **一条规矩，如果只在做某类任务时才需要想起来 → skill。**

- "DECISIONS 只追加" —— 每次写文件都该守，不需要"调用" → **约定**
- "给倍数前先判定资产性质" —— 只在估值时才需要 → **skill**

**为什么必须两样都有**：没有 skill，你会想漏；**没有约定，你会想到了但留不住**——
三个月后同一个坑再踩一遍，因为当初的判断散落在聊天记录和十几份文件里。
**skill 决定认知的质量，约定决定认知的复利。**

## 1. 文件三分法：状态 / 过程 / 产物

一份文件在动手写之前，先定它属于哪一类。**这是本约定的地基，其余全部由它派生。**

| 类型 | 特征 | 怎么写 |
|---|---|---|
| **状态**（现在是什么） | 只有一份，永远最新 | **覆盖**。不带日期版本号 |
| **过程**（怎么变成这样） | 只追加，永不修改已有条目 | **追加** |
| **产物**（算/生成出来的） | 可随时重新生成，删了不心疼 | 程序写；可带日期版本号 |

**判据（最容易判错的是"产物"）：**

> **能不能从「状态」重新生成？**
> 能 → 产物；**不能 → 它其实是状态，只是伪装成产物。孤儿文件全部来自这里。**

**状态层内部还要再分一刀**（这一刀不分，目标态文档必然烂掉）：

| | 回答什么 | 变化速度 |
|---|---|---|
| **目标态** | 要造成什么样 | 很慢 |
| **当前态** | 现在跑到哪了、下一步干什么 | 每轮都改 |

> **目标态文档里不许出现"当前跑出来的数"。** 需要提到某个量，就写它的
> **名字 ＋ 字段名 ＋ 去哪查**，不写它今天等于多少。
> 判据：**改一个参数重跑，这份文件需不需要改？需要 → 那段写错了地方。**

### 再加一个维度：谁读（2026-09-20 新增）

三分法管"怎么存"，这一刀管"怎么写"。**写法跟着读者走。**

| 类别 | 典型文件 | 写法 |
|---|---|---|
| **A · 给人读**（也给新会话读） | 第 0 章与各章正文、每道门／每轮的一页纸、`交接.md`、版本谱系、`口径/` 白话复核件、阶段性工作计划 | **融合改写，不在文末追加**；结论先行；一件事一个家；不写"上一版如何"；改了哪里由 AI **在对话里**逐条说明（对话就是变更说明，文件保持干净）；尽量短 |
| **B · 人写、程序读** | `narrative/*.src.md`；参数试算用的 Excel | 人话正文＋占位符；格式由程序检查，人不用记规则 |
| **C · 给机器读**（AI 与程序；人按需查） | `DECISIONS.md`（人只看顶部索引表）、`src/`、`configs/`、`outputs/*.json`、`audit/*.json`、AI 的记忆 | AI 自行维护，只追加或程序生成；不要求好读，但要可检索 |

> **判据：这份文件人会不会从头读到尾？会 → A 类，订正必须融进正文。**
> 教训：一份给人读的工作计划被当成过程记录、在文末追加订正表——利于机读，人读不下去。
> **人日常只需读三样**：第 0 章（当前论点与放弃条件）、当前这一轮的一页纸、被改动的章节正文。

### A 类文件的交稿清单：写成常识能读懂的话（2026-09-21 新增）

**由来**：一页纸写得"每个数都对、整体读不懂"，研究者读不出推理主线；同一个意思在对话里用白话讲一遍就清楚了。
**判据：投资靠常识判断生意能不能做。一个结论说不成常识话，要么没想清楚，要么在用术语掩盖没想清楚。**
A 类文件交稿前，AI 逐条过这张清单（靠清单，不靠自觉）：

| # | 规矩 | 怎么验证做到了 |
|---|---|---|
| 1 | **读者是一个聪明但不懂这一行的人**，每句话他都能复述 | AI 交稿前先用三句话复述全文；复述不出来就重写 |
| 2 | **正文按"五问"组织**：问的是什么／答案（一句话）／凭什么（三到五步，每步一句常识＋一个数）／什么情况下我错了／下一步查什么。四道门模板的七节照用，但每节按这个次序写 | 正文里找得到这五样，且答案在最前面 |
| 3 | **详细算式与大表格写在同一文件末尾的"附录"**，不另开文件；正文只写"算式见附录第几条"。谁都能拿计算器逐行核 | 正文每个数都能在附录找到算式 |
| 4 | **术语规则**：商务、财务的一般说法照常用，但第一次出现时说清楚是什么对什么。三条定死：① 不说"承重数"，说**关键变量**；② "覆盖倍数"写全为**EBITDA 对资本开支（按资本成本折成每年要还的钱）的覆盖倍数**；③ 用"乘数"时写明**对谁、在哪个维度上乘** | 正文里没有"承重数"；覆盖倍数与乘数第一次出现处都有这句说明 |
| 5 | **每个数都说"这意味着什么"**，并跟一个常识参照比（存款利率、债券收益、同行报价……） | 正文里没有孤零零的数 |
| 6 | **正文每节最多一张表、最多五行**；再多就进附录 | 数一遍 |
| 7 | **每个结论后跟一句常识检验**：这符不符合一个做生意的人的直觉？不符合，先怀疑自己算错了 | 每个结论后有这一句 |
| 8 | **交稿自检**：研究者只读正文，能答出"结论是什么、凭什么、什么会让它错"。答不出来是 AI 的问题 | 研究者反馈 |
| 9 | **对话回复同样执行**：先结论、后理由；不讲"我改了哪些文件"，讲"算了什么、结果是什么" | — |
| 10 | **每个数第一次出现，说清来历、单位和时间尺度**：观测／推算／设定三选一；"每度""每月""每车"写全（例：不写"包含 48.5 度"，写"513 度的车每月含 24,880 度"）；设定且无出处的数要明说 | 附录有"输入的数从哪来"表，每个输入数都在表里 |
| 11 | **不留只说不算的话**：提出一个威胁或利好（"快充电芯能缩小差距""只会更狠"），必须给出它会让结论变多少；没有数据就明说"没找到数据"，并给出临界值（到什么程度结论会变） | 正文里没有只有定性、没有量级的判断 |
| 12 | **自造的说法不进正文**（如"穿过零的借钱成本"）；每个概念用读者已有的词说一遍，必要时在文首列"本页用到的词" | 研究者读到没卡住 |

> 纪律登记：本清单约束所有 A 类文件；检查时点＝每次交稿前；验证方式＝上表第三列。

## 2. 目录与准入判据

**文件山的定义不是"文件多"，是「不知道一个文件该放哪 / 不知道去哪找」。**
只要每个目录有一句明确的准入判据，文件多不是问题——
报告写完会有八章 ＋ 若干专题，那是正常的；**散在根目录才是文件山**。

### 2.1 根目录只放「纲领」，五份，硬规则

| 文件 | 回答什么 | 类型 |
|---|---|---|
| `README.md` | **一分钟看懂**：这是什么、怎么跑、去哪找 | 状态·导航 |
| `研究项目约定.md` | **工作台**：文件怎么放、怎么协作 | 状态·约定（可复制到新项目） |
| `框架提案.md` | **要造成什么样**（成果复杂时才需要） | 状态·目标态 |
| `交接.md` | **现在到哪了、下一步干什么** | 状态·当前态 |
| `DECISIONS.md` | **为什么变成这样** | 过程·按主题 |

> **判据：一个新文件想进根目录 → 问它是不是"每次开工都要读的纲领"。不是 → 进子目录。**

### 2.2 子目录，每个一句准入判据

```
<项目根>/
├── configs/              参数
├── src/                  程序
├── 口径/                 跨环节的口径与方法论证
├── narrative/
│   ├── chapters/         报告各章
│   └── topics/           报告论证专题
├── audit/                台账
├── outputs/              生成物
└── _archive/             已被取代的
```

| 目录 | 准入判据 |
|---|---|
| `configs/` | 是一个**可调的输入值**，且**带信源**（没有信源的必须显式标"经验假设"） |
| `src/` | 是**计算逻辑**。**唯一引擎**——同一件事不允许有第二处实现 |
| `口径/` | **一个口径/方法问题需要独立论证，且被多处引用。** 它既支撑定量计算，也能推出定性判断 |
| `narrative/chapters/` | 对应骨架表里的一章。**数量固定，不允许中途增加** |
| `narrative/topics/` | 满足任一：**① 两章以上引用；② 更新周期与模型无关；③ 是一条已定决策的完整论证** |
| `audit/` | 是一份**逐条核对**的清单（信源台账、链路审计） |
| `templates/` | 是**输出格式模板**，被 `src/` 引用。**不含任何业务数字与口径判断**——判据同 HTML 边界：把模板删掉重写，报告结论一个字不变 |
| `outputs/` | **能从上面这些重新生成。** 可带日期版本号 |
| `_archive/` | **职责已被别的文件完整接管**，且**做过覆盖检查**（见 2.4） |

**`口径/` 与 `narrative/topics/` 容易混，它们的读者不同：**

| | 读者 | 写什么 |
|---|---|---|
| `口径/` | 要**核查或复用这套算法**的人（也是未来的你） | 这个数怎么算的、口径为什么这么定、可迁移的方法 |
| `narrative/topics/` | 读报告的**投资人** | 投资论证的片段 |

### 2.2.0 过程文件的主语：谁是主角

两份过程文件**用途不同，主语也不同**。不声明主语，AI 会默认用自己的视角写——
**那是它的自然位置**，因为它写的是自己刚做过的事。

| 文件 | **主语** | 谁主笔 | 用途 | AI 在里面的位置 |
|---|---|---|---|---|
| `DECISIONS.md` | **我们**（共同的决定） | AI 起草，人 review | ① 人回顾判断的转折点 ② **训练个人数字分身的语料** | **人与 AI 的交互过程都要记**——交互本身就是语料，纠错反复尤其是 |
| `研究历史记录.md` | **我**（人） | **AI 每轮主动起草，人在草稿上改** | **人自己的工作日志** | **只作素材与启发出现，用第三人称。AI 必须主动起草**——但**主语是人**，起草时就用人的视角，不要留给人做视角转换 |

**日志的三条写法（`研究历史记录.md` 专用）：**

1. **小节标题写结论，不写事件。**
   ✅「标准可以类比为品牌价值，在未被商业社会定价前不能加」
   ❌「AI 给公式加了个 O，被打掉了」
2. **只记重要变更的背景、过程、结果。**
   AI 的自省、纠错的心理过程、"我错在哪"——**全部归 `DECISIONS.md`，不进日志。**
3. **段首一句定主题**，让三个月后的自己一眼看出这天在想什么。

> **为什么是"AI 主动起草"而不是"AI 不写"**（2026-09-06 修正）：
> 日志的价值在人的判断，但**打字不是判断**。让 AI 每轮主动起一稿、人在上面删改，
> 比人从空白页开始快得多——**协作的分工是"AI 出材料与结构，人出判断与取舍"，
> 不是"谁的文件谁从头写"。**
> 代价是 AI 会把视角写歪，**所以视角要求写进起草规则里，而不是留给人事后转换。**

> **可迁移的一条：任何人机协作产出的文档，都要显式声明主语。**
> 主语不定，产出就会漂向 AI 的视角——它不是故意的，它只是在写自己看得见的那一半。

### 2.2.1 一条贯穿全部纲领文件的纪律：可独立阅读

> 五份纲领文件里，出现的每个专有名词，**要么在所在文件内定义，要么给出"去哪查"的指针**。
> **不允许出现只有作者当时知道的编号或缩写**（`T1`、`P7`、`方案乙` 这类）。

配一张**术语表**放在文件末尾，是最省事的落地方式。

> ⚠️ 写下任何一条纪律时，同时写清三件事：**约束谁（作用域）、什么时候检查（触发点）、
> 怎么验证执行了（可观察的证据）。** 三件缺一件，这条纪律就会在某个角落失效。

### 2.3 两条防堆山的硬规则

**规则一 · 新建文件三问**

> 1. 它是**状态、过程、还是产物**？
> 2. 已有文件里，有没有哪一份的职责涵盖它？**有 → 写进那一份，不新建。**
> 3. 如果新建，它进哪个目录？**答不上来 → 说明目录体系缺一类，先补判据再建文件。**

第 3 问是关键：**它把"这个放哪"从麻烦变成信号**——
答不上来不是你笨，是分类学缺了一格。

**规则二 · 章数固定，专题按判据生长**

`chapters/` 数量固定。需要更多篇幅 → **提为 `topics/` 专题，不是新增章**。
这保证报告结构稳定：**骨架不动，血肉按判据长。**

### 2.4 归档必须先做「覆盖检查」

> ⚠️ **覆盖检查是必要条件，不是充分条件。**
> 充分条件是**接管方本身已经过人的验收**——
> **覆盖检查回答"能不能接管"，验收回答"接住了没有"；前者 AI 能做，后者只有人能做。**
> 少了后者就归档，是把"我认为覆盖了"当成了"确实覆盖了"。

一份文件要进 `_archive/`，先**逐节确认它的每一节，职责现在归谁**。

> **没做覆盖检查就归档 ＝ 丢东西；不归档又留着 ＝ 留一个会误导人的旧真相。**
> 两害相权，先做检查。**检查结果写进 `DECISIONS.md`**（哪节归了谁、哪节没人接、怎么处理）。

早期的"逻辑记录类"文件（写在还没有 `框架提案.md`／`口径/` 之前的那些）
最容易卡在这里——它们通常**大部分已被接管、小部分还没有**。
不检查就归档会丢掉那小部分；而它往往正是当初想得最细的地方。

### 2.5 本项目之外

有些文件属于**同一研究但不属于本子项目**（比如整个研究方向的日志，
它比这个子项目更早、覆盖面更宽）。**不要为了整齐把它们搬进来**——
在 `README.md` 里给一句指针即可。**目录整洁的目的是找得到，不是对称。**

## 3. `DECISIONS.md`：本约定里最值钱的一份

**它记的是研究过程中的所有转折，不只是代码改动。** 四类，每条必须标：

| 类型 | 记什么 |
|---|---|
| **研究判断** | 对研究对象本身的看法变了 ← **最值钱** |
| 建模口径 | 公式／字段／算法变了 |
| 方法论 | 怎么研究的方法变了 |
| 工作方式 | 文件治理、协作方式变了 |

> **建模 bug 谁都会犯，判断错在哪才是研究者本人。**
> 「研究判断」这一类既是最好的语料，也是报告"诚实清单"章的唯一素材来源。

### 条目格式：六栏 ＋ 两个标记

```markdown
## YYYY-MM-DD · 一句话标题                        [类型]

**当时怎么想的**   ← 不是"背景"，是当时脑子里的模型
**触发**           ← 什么事让你发现不对
**查下来**         ← 事实，带数字带出处
**改成什么**       ← 具体到字段/文件/公式
**影响**           ← 哪些结论跟着变了
**我错在哪 · 学到什么**  ← 全文件最值钱的一栏，见下

→skill: <哪个 skill> · <哪一节>
```

**「我错在哪·学到什么」这一栏的写法**（其余五栏是记录，这一栏是资产）：

1. 先说**错在哪一层**——是算错了、想漏了，还是**问错了问题**
2. 再抽出一条**可迁移的判据**，写成"下次遇到 X，先问 Y"的形式
3. 判据要**能判掉具体的错**，不能是"要仔细""要注意"

> **反例**："以后要注意参数来源。"
> **正例**："任何一个'期限/寿命'参数，先问它约束的是**一个资产单元**还是**整门生意**——
> 前者是技术参数，后者是资产类别判定，必须去查法律/合约权利，不能从第三方评估报告里借。"

**`→skill:` 标记的意义：不要让沉淀依赖回忆，让它依赖标记。**
跑通一遍之后写 skill ＝ **把标记过的条目归拢重写**，不是"回忆我学到了什么"。
**内容清单会变，这个机制不会。**

### 三条格式纪律

1. **只追加，永不修改已有条目。** 判断变了就追加一条新的，写明它深化/推翻了哪一条。
   **纠错本身就是最有价值的语料，抹掉它等于抹掉判断的转折点。**
2. **索引表必须始终完整。** 索引是导航件（可从条目重新生成），
   "只追加"不约束它——**一份不全的索引比没有索引更坏。**
3. **每条改动必配一条条目。** git 答"改了什么"，DECISIONS 答"为什么"。

## 4. 协作协议（人 ＋ AI）

| 步 | 谁 | 做什么 |
|---|---|---|
| **1** | **AI** | **先说明分析与方案**：改什么、为什么、影响哪些文件、有哪些待拍板项。**这一步不许跳** |
| 2 | 人 | 说「过 / 停 / 改」，或先答待拍板项 |
| 3 | AI | 改，**重跑通过**才算数；落盘后说明改了哪几个文件、每个改了什么 |
| 4 | 人 | IDE 里 `git diff` 看具体行，`git commit -m "<一句话> · 见 DECISIONS <日期>"` |

> **review 的闸门放在"看方案"而不是"看 diff"**：更早、更省事，
> 而且它拦得住**方向性错误**——diff 只能拦实现错误。

**四条硬约束：**

1. **一次交付只改一个关注点。** 跨越太多文件就拆两次。
2. **每个改动必须配一条 DECISIONS 条目。**
3. **改动点在代码/文档里留注释**，写明改了什么口径、为什么、指向哪条 DECISIONS。
4. **讨论不留在对话里。** 一轮讨论产生了有价值的判断，**当轮就落进文件**：

| 产生了什么 | 当轮落到哪 |
|---|---|
| 一个判断从 A 变成 B | `DECISIONS.md` 一条（带类型 ＋ `→skill:`） |
| 当天的思路、读到的东西、发散 | `研究历史记录.md` 一段 |
| 目标态变了 | `框架提案.md` |
| 当前态变了 | `交接.md` |
| 口径变了 | `<口径文档>.md` |

**每轮结束前，AI 逐行走一遍上面这张表**，五行逐行答"有／无"，有则当轮落盘。

> ⚠️ **不要写成"自问一次"——自问靠记忆，走表靠机制。**
> 这条规矩第一次写成"自问"的当轮，就漏掉了当前态文件（`交接.md`）没更新。
> **凡是靠"记得"执行的规矩，都要改成靠"走一张固定的表"执行。**
> 这与 `→skill:` 标记是同一条道理：**不要让纪律依赖回忆，让它依赖清单。**

**第八条 · 模型分工：判断用强模型，执行可降级；一页纸必过异构审阅。**（2026-09-20 新增）

| 工作 | 用什么模型 | 为什么 |
|---|---|---|
| **写一页纸、回应人的质疑**（从数字里找结构、给出对人不利但成立的反驳） | 当前能用的最强模型 | 差别主要出在这两步 |
| **执行**（改参数、改章节、写记录、找信源、抓跟踪数据） | 可降一档 | 按部就班；约束已落在约定、协议与登记表里，对单个模型的依赖低 |
| **审一页纸** | **另一家厂商、没有项目背景的模型**（见 §4.1「异构审阅」） | 同一模型另开对话，思路仍同源 |

**该换回强模型的三个信号**：开始顺着人说；不再主动指出对人不利的地方；同类错误复发（本项目的典型：把一个细分市场的数据搬到另一个）。

**第七条 · 每次改动前，先取人手上的最新版本，不用自己的缓存。**

AI 的工作副本会过期——**人在两轮之间会直接改文件**：改措辞、重编号、换视角、删段落。
从缓存写回，会把人的修改整体抹掉，**而且在 git diff 里看起来像是 AI 主动改回去的，
很难认出那是一次覆盖**。三条：

1. **改任何一份文件之前，重新取它的当前版本**——上一轮取过不算数
2. **写回时带上取版本时记录的时间戳**，让冲突变成报错，而不是静默覆盖
3. **先适配人的修改，再叠自己的改动**——重命名、重编号、换视角都要跟着走一遍全仓引用，
   不能只改自己新写的那部分

> **判据：AI 手里的永远是副本，人手里的才是正本。**
> 副本与正本不一致时，**一律以正本为准**，哪怕副本"更新"。

**第六条 · 纪律登记表：每条纪律必须登记它在哪儿生效。**

一条纪律写下来还不够——**必须同时登记三件事**，缺一件它就会在某个角落失效：

| 列 | 回答 |
|---|---|
| **约束谁** | 作用域：哪些文件／哪类动作 |
| **什么时候检查** | 触发点：**"做 Y 之前先做 X"**，不能是"随时注意" |
| **怎么验证执行了** | 一条**可观察**的证据，不是"我记得做了" |

> **为什么要有这张表，而不是把要求写在各条纪律旁边**：写在旁边＝散落，
> 散落＝只能靠记忆调用，而**靠记忆调用正是这些纪律要治的病**。
> 实际教训：同一族失败（规矩对、投放位置错）连续发生了四次，
> 每次都是事后补一条、补在"发现问题的那份文件"里，**从来没有一个地方把它们连同触发点一起列出来。**

**两条派生规则：**

1. **凡是写下"材料已齐，见 X"的地方，必须同时写"做 Y 之前先读 X"。**
   **指针不绑触发条件 ＝ 没有指针**——写指针的人和用指针的人不是同一时刻的同一个人。
2. **一条纪律每复发一次，就往"更不依赖记忆"的方向改一格**：
   自问 → 走固定的表 → 进登记表 → 最终变成流程里的一个**前置动作**。

**登记表本身放在 `交接.md`（当前态），因为每个项目的触发点不同。**

**第五条 · 每一项任务都必须有 owner，不许留空档。**

任务清单每一行必须有「**谁做**」，取值只有三种：

| owner | 含义 | AI 的义务 |
|---|---|---|
| **AI** | AI 独立完成 | 做完报告改了什么 |
| **你** | 人执行 | **必须给出可直接执行的具体动作**——命令、路径、参数，不能只说"需要检查一下" |
| **AI→你** | AI 产出、人执行不可逆的那一步 | 先给产出物供判断，人确认后才执行 |

**分工原则：**
- **判断与产出 → AI**（读、比对、生成内容）
- **在人的机器上执行的命令、以及不可逆的文件操作（`git mv`、删除、跑长任务）→ 人**

> **"待办"不是任务。"谁、在什么时候、用什么命令、做什么"才是任务。**
> 一条没有 owner 的待办，等于两边都以为对方会做——**这是协作里最常见的空档。**

## 4.1 复核协议：按「人不读程序」这个前提来定（2026-09-15 新增）

**这一节的由来是一次失败。** 连续多轮改动全部落在 `src/`、`configs/`、`narrative/`，
每轮结尾我都报告"已完成、重跑通过"。而人在这个项目里的实际能力状态是：
**不读程序，只打得开 `outputs/` 里那张沙盘 HTML。** 于是每一轮的"完成"都无法被复核，
只能被相信。

> **一个无法被复核的交付，不管对错，都不是协作，是托管。**
> 而托管一个会犯错、而且已经犯过十几次错的对象，是最坏的一种安排。

**根因不在人不懂程序，在 AI 没有按合作者的能力状态设计交付物。**
"看 `git diff`"这条闸门（§4 第 4 步）默认了人能读懂 diff 里的语义——
在这个项目里这个默认不成立。所以 §4 的第 4 步在本项目**降级为可选**，
由下面这条硬约束取代。

### 硬约束：每一轮改动必须在沙盘 HTML 上留下痕迹

**判据一句话：** 打开 `outputs/换电沙盘_v4.3.html`，
**看不出这一轮改了什么的交付，等于没交付。**

落地成两件东西，分工是刻意的：

| | 谁写 | 写什么 | 在哪 |
|---|---|---|---|
| **说法** | **AI 手写** | 这一轮改了什么、为什么、你该盯哪个读数、**我跑之前的预期** | `configs/changelog.toml` |
| **读数** | **程序自动** | 三档关键读数，每次构建自己追加一条（同日覆盖） | `audit/baseline_history.json` |

沙盘「◈ 复核区」把两者**并排**显示：左说明、右读数（上一轮 → 本轮，变了的标红绿）。

> **为什么必须是两件而不是一件**：只有说法的变更记录是公关稿；只有数字的变更记录看不懂。
> 并排放的意义在于**它们可以互相拆穿**——
> 我说"基线不该动"而右表三档全变了色，不需要懂程序也知道出事了。

**`expect` 字段必须在跑之前写。** 跑完再填的不是预期，是解释。
预期与实际读数不符时，只有两条出路：改 `expect` 并说明为什么猜错，或者承认改错了。

### 配套：改了"看不见的东西"怎么办

有些改动天然不产生读数变化（口径修正、加保护、改注释）。**这类改动更要留痕**，
因为它最容易被说成"我改了很多"而无从查证。规矩是：

1. `changelog.toml` 的 `watch` 写明**"哪个数不该动"**，
   右表全是黑字就是通过——**"没动"本身是一个可复核的结论**。
2. 新增的保护（断言、lint）必须当轮做**负向测试**：
   故意把它该拦的东西写错一次，确认它真的中断，并把这句话写进 DECISIONS。
   **没做过负向测试的保护，不许声称"已加保护"**——它可能一次都不会触发。

### 三条给 AI 的禁令

1. **不许把"重跑通过"当成交付完成。** 重跑通过只说明程序没崩，不说明改对了。
2. **不许用"见 `DECISIONS.md` 某条"来代替沙盘上的痕迹。** 那是给未来的自己看的，不是给人复核的。
3. **不许一轮改超过一个关注点**（§4 硬约束 1 的加强版）：
   复核区一次只能讲清楚一件事，两件事混在一轮里，读数变了也说不清是哪件引起的。

### 人这一侧只需要做三件事

1. 打开沙盘，看**复核区**：左边那段话说的，右边的数对不对得上。
2. 看**事件表**：每个事件的触发条件、动了哪些参数、值多少钱。
3. 拨**一键三档**，看读数和结论卡是否跟着动。

> 看不懂的地方直接问"这个数是什么意思"——**说不清楚就是我的问题，不是你的**。

### 异构审阅：让一个没有历史负担、头脑不一样的模型来挑错（2026-09-20 新增）

沙盘复核管的是"程序的数对不对得上"；它管不了"这个数该不该这么取"。后者靠异构审阅。

- **谁来审**：**不同厂商、完全没有本项目背景**的 LLM。理由与"AI 审人"相同——没有历史负担才逼得出真问题。
- **审什么**：只给那一页白话复核件（算式、信源原文摘录、口径）。**不给结论、不给讨论过程、不给代码。**
- **只让它挑三类错**：① 把 A 细分市场的数据用在 B 细分市场；② 量纲或口径对不上；③ 信源原文并没有说这句话。
  外加一问：**"哪一个数如果错了，结论会翻？"**
- **怎么收**：审阅意见原文存档；每条只有三种处置——采纳并改／驳回并写理由／挂账。
- **什么时候做**：每份承重的一页纸落盘之前。后续可做成 agent 调度。

## 5. 版本与留痕

- **留痕用 git，不用复制目录。** 复制目录的留痕是假的——你看得到两个版本，
  **看不到哪一行为什么变**。
- **一个仓库只能有一个 `.git`，不能嵌套。** 诊断：`git status --short`
  （`U`＝未跟踪 `M`＝改过未提交 `A`＝已加待提交，无输出＝干净）。
- **版本号只长在发布产物上**（`outputs/xxx_YYYYMMDD.html`），**不长在源文件上**。
  源目录里出现 `_v2` `_v3` `_final` 就是文件山的开始。
- `.gitignore` 至少：`__pycache__/`、`*.pyc`、`~$*`、`*.tmp`

## 6. 计算与信源的硬规则

这几条不属于任何单个 skill，是任何定量研究项目都该守的：

1. **参数与信源绑定**：每个参数带一行出处。**没有出处的参数必须显式标"经验假设"。**
2. **一套测算整套引用，不要各取一项。** 自洽测算里参数相互约束
   （高电耗对应高负载对应低里程），拆开拼出来的组合可能**在物理上根本不存在**。
3. **引用复合指标（TCO / IRR / 回本周期）前，先核对它的三个最敏感输入是不是当期值。**
   找不到它的假设 → 这个结论不能引用，只能当"有人这么说过"。
4. **宣发口径的数字不能做输入，只能做交叉验证。** 公司自己说出来的规划数，
   功能是表达决心，不是表达测算。
5. **断言写成恒等式，不要写成不等式。** `≤` 只能证伪不能证实。
   更进一步：**好的恒等式应当按构造成立**——把两边写成同一组数的两种排列。
6. **容差只用来吸收浮点误差，不用来吸收口径错误。**
   容差 > 1e-6 量级时都要问：这个残差是数值误差，还是我还没查清的错？
7. **写任何新东西之前，先搜既有仓库。**
   一个做了很久的研究项目，**大量基础工作已经做过，只是散落着**。
   动笔前先在**项目根目录整树**里搜关键词（文件名 ＋ 全文），确认是否已有专题、口径或数据。
   **判据：一份"我以为要新写"的材料，八成已经写过一半。**
   代价：搜一次几分钟；不搜的代价是**重写一遍、而且和旧稿不一致**——
   于是文件山又厚一层。
8. **口径文档里的数字分三类，处理方式不同**：
   **① 输入参数** → home 在 `configs/base.toml`，口径文档只写**键名 ＋ 取数理由**，不写数值；
   **② 计算结果** → home 在 `configs/metrics.toml` 的 `label`（`outputs/facts.json` 只是装配产物，不是定义处），写**占位符**；
   **③ 口径本身的取值**（"取小"、"取下沿"、分几段） → **就是口径文档的内容，写数字**。
   **判据：改一个参数重跑，这份文件需不需要改？需要 → 那一段写的是别人的数。**
   （这条原来只约束目标态文档，本轮作用域扩到口径层。）
9. **输入事实只有一个家：`configs/base.toml`（2026-09-13 下午定稿，取代同日早先"第三个家 external_facts.toml"与"末尾 [[input_fact]] 登记区"两版方案）。**
   模型按用途只有**输入/输出**两类：输入全在 `base.toml`，输出全在 `metrics.toml`。
   要进叙述的输入事实在 base 内分两种形态：
   * **就地信封**（20 个）：被程序/滑块直接消费的参数（兑现年、driver、
     外部锚点、阈值）住在它被消费的功能段，在原表内写虚线子表——
     `<键>.v` 是值的唯一住处（程序读它，加载时自动解包成裸标量，改档即时生效），
     label/unit/decimals/scale/fmt/note/src 是同住的呈现要素；注册表 key 就是
     **点分路径本身**（如 `meta.target_year`），不造别名、不另开登记区；
   * **`[[external_quote]]` 引述卡片**（16 条）：只被叙述引用、**不进任何计算**的外部原文引述
     （研报倍数、JPM TCO 对照），走 `ext.*` 命名空间，自带 value（代表值）/text（可写区间），
     每条必填 `src`（信源台账的 `src.*` key，URL 只住在台账）与 `as_of`（抓取日期）。
   **不能写"引自本仓库某个老版本文档"**——自己的过程老稿会被归档，指针会断；
   而且任何一份纲领文件都该**自成体系、不依赖老文档即可独立阅读**。
   老版本只能作为"我在哪儿看到的"线索，**不是信源本身**。
   唯一例外：**权威外部报告的仓库内归档全文**（如 `media/JPM_重卡电动化_英中对照.md`）
   经台账 `src.*` 登记相对路径后可作信源，链接经台账机械校验必须真实存在——
   它是外部信源的归档，不是我们自己的过程稿。
   `metrics.toml` 只登记模型输出（118 条 `at`），不挂配置名片；`facts.py` 不定义任何一条。
10. **一段描述性逻辑的接管方，必须是同样给人读的东西。**
   **"有程序实现" ≠ "有人接管"**——程序接管的是执行，不是表达，**读者不会去读代码**。
   **判据：把这段话删掉，还有没有人能从别处读到同样的意思？读代码不算。**
11. **叙述层不许出现字面数字**（年份等白名单除外），一律写占位符由装配时注入。
   检查从"字符串比对"退化成"文件里还有没有裸数字"，一个正则就能穷尽。
12. **数取不到的时候必须闹出动静，不许沉默。**
   `read_metrics` 取不到值不是给 NaN 就完了——`nan亿元` 和"这个数今天算不出来"
   在页面上完全同形，事后极难追回，比给个错值更贵（错值当场就会被人问）。
   分两类处理：**路径走不通／调用方漏传 cfg → 中断并逐条点名**；
   **路径通但程序主动给空**（如 REIT 回笼倍数派生失败）→ 集中报一次，不冒充成数。
   判据：任何一个"取不到"如果能在页面上安静地流过去，这条纪律就还没落地。
13. **一个 key 一个定义，一个数一条取数路径；孤儿即删。**
   * 同一个 key 定义两次 = 后者静默覆盖前者 → 加载即中断；
   * 撞名防线（2026-09-13 再改）：手写事实层已删，不再有 `mirror=` 互校；
     base 的就地信封、`[[external_quote]]` 与信源台账的 key、中文名只要撞上
     `metrics.toml` 的 key/label，`lab.load_metrics()` 就在加载期（唯一裁判点）中断，
     `facts.check_no_duplicate()` 保留为每条管线的复述防线——一词一名靠**禁撞**保证，不靠维护第二份值；
   * **差 100 倍（比值 vs 百分数）单独报错**：本仓库占比一律以百分数存储；
   * **定义了但没人引用的事实 = 负债**（它随时可能被人当成"第二套名字"用），直接删；
     随之变成死代码的取值助手一并删，留着就是"一个算式两个出处"。
14. **明细落快照、标量进字典（2026-09-13 定）。** 逐年/逐池/逐车型的过程矩阵住快照
    dataclass（如 `ScaleResult.yearly_stock`），`metrics.toml` 只注册兑现年标量；
    矩阵兑现年列必须与既有标量**硬对齐**（同算式复刻或断言，容差只吸收取整尾差）。
    存量不扣退役、流量不等于存量——两个口径不许互相冒充。
15. **以终为始：先定要论证的命题，再倒推需要看什么；不许只写第一层影响。**（2026-09-18 立）
    一层影响写完就停笔，读者拿不到结论，而作者往往以为自己已经论证过了——
    **这不是思维跳跃，是根本没有从终点往回推。**
    动笔前先写下这三行，写不出来就说明还不能动笔：
    * **要判的是什么？**（一句话的命题，必须可判真假，不是"分析一下某某"）
    * **判它需要哪几个数？**（把命题拆成必须同时成立的条件，逐条对应到读数）
    * **看到什么会让我改判？**（证伪条件；写不出来说明命题不可证伪，要重写）

    两条自查判据：
    * **末端判据**：这一段的最后一句，是不是**直接回答了开头那个命题**？
      如果最后一句是一个中间量（折旧、时长、份额、投资强度……），那就是只写了第一层——
      **中间量不是结论，它只是通往结论的一段路。**
    * **接力判据**：每一个中间量后面，是否都紧跟着"所以它怎么影响最终结论"？
      **断在哪里，读者就在哪里掉队**，而作者通常看不见那个断点，因为他脑子里那一段是连着的。

    本项目的两个实例（都是先犯了、再改的）：
    * 算了产线的**单位投资强度与折旧**就收笔——可要判的是"车企自建划不划算"，
      那就必须一路算到**自建的单位电池全成本、与外购价相比**，并给出**打平所需的外购价**这个可证伪刻度；
    * 比较超充与换电时，把差异拆成了几项、却只量化了**时间价值**一项——
      那只是定性，说不出"哪种场景、在什么条件下被取代"。
      必须把每一项都折成**同一单位的年化金额**，相加后给出**分场景乘分档的净优势矩阵**，
      并让矩阵的变号位置与另一条独立算法（多买一块电池的内部收益率）**收敛到同一个点**。

    配套的一条：**中间量必须带单位和方向。**给出"产线折旧每 kWh 多少钱"之后，
    要接"所以自建每度贵多少、贵百分之几"；**没有方向的中间量，等于没写。**

16. **用户视角：报告是给读者用的，不是给作者记账的。**（2026-09-18 立，因为同一类错误已经犯了很多轮）
    这一类错误的共同点是——**作者把自己的工作过程当成了内容**。它有五种形态，逐条对照自查：

    | 形态 | 长什么样 | 判据 |
    |---|---|---|
    | **① 版本日记** | 「上一版把 X 合成一项，那是个错误的合并」「这比上一版少了一条」「这一条要明确撤回」 | **删掉这句话，读者会少懂什么？**答"什么都不少"就删。版本间的变化写进 `DECISIONS.md`，正文只留当前判断 |
    | **② 只写怎么算，不写在算什么** | 「折成年化净差额（越低越有利于换电）」——读者不知道这个数是什么、正负各意味着什么 | **每个表格/读数前先说它是什么量、正负各对应什么结论**，再说怎么算 |
    | **③ 结论离读数太远** | 给出中间量就收笔，让读者自己走完最后三步 | 见第 15 条（以终为始）。**两条是同一个病的两面：15 条管"算到底"，16 条管"说到底"** |
    | **④ 同一节里混用两个方向** | 一张表"正数＝换电贵"，隔壁表"正数＝换电好"，中间不说明 | **一节之内只能有一个符号方向**；必须换向时，在换的那一行明写"从这里开始方向反过来" |
    | **⑤ 该收进专题的推导留在正文** | 正文连着写四步推导、参数表、口径偏向，读者读到第三段已经忘了要判什么 | **正文只放结论表 ＋ 怎么读；推导、参数来源、口径偏向进专题。**判据：正文里任何一段，读者跳过它还能不能看懂结论——能，就该进专题 |

    **一条总判据（写完每一节都过一遍）：**
    > **把这一节给一个只关心"该不该买"的读者看，他会不会问"所以呢"？**
    > 会，就是没写完；他要是问"你在说什么"，就是 ② 或 ④。

    **为什么单列一条而不是并进第 15 条**：第 15 条是**论证的完整性**（算到不算到），
    第 16 条是**表达的立场**（站在谁的位置写）。**一段可以论证完整、却依然是写给作者自己看的。**

17. **情景一律三档：悲观／中性／乐观。**（2026-09-21 立）
    任何进结论的不确定参数都给三档，每档写明取值理由；**中性档不得高于同口径的实测或实验值**
    （例：实验室 25℃ 循环 3,760 次，中性档就不能取 4,000）；乐观档可用厂家官宣，但要打折并写明为什么打折。
    两个参数联动时（例：电池寿命与月租），给 3×3 表，并标出哪几格在经济上"两头都成立"——
    **只给两档，读者无法判断你站在区间的哪一端。**
18. **动手前先读已有成果，而且把"读"绑到具体的触发点上**（第 7 条的执行版，2026-09-21 立，因为第 7 条写了仍被跳过）：
    - **找信源之前**，先查 `audit/信源审计台账.md` 主表；已登记的直接引 key，**不重复检索**；新找到的先登记进主表，
      下游文件列出的信源只能是主表的子集，并带可点击链接；「用于」一列写最终的家（章节或参数键），
      临时文件（如四道门一页纸）的用途用〔门N：…〕标出，归档时删标记并核对章节已引用；
    - **讨论"换电对充电""电池值多少"这类本质问题之前**，先读第 2 章「业务本质」与专题
      `业务本质_第一性原理拆解`——结论要从那里的七步链推下来，不要从头重新推；
    - **定参数取值之前**，先看 `base.toml` 该参数注释里已有的推导链与台账批次审计行，改值要说明比原推导好在哪。
19. **结论三档一起报；越过门槛的那一档，把造成它的参数逐个列出来。**（2026-09-22 立，研究者要求）
    - 正文给结论时，悲观／中性／乐观三档的读数并排给，不许只写中性——只写中性，读者不知道区间两端有没有翻符号。
    - 任何一档跌破门槛（或乐观档明显高出常识），必须附**拆解**：从中性出发，每次只拨一个参数看读数变多少，再把起作用的几个叠加；
      列出每个参数在该档取什么值、这个值会不会真的发生（有无观测、是不是今天的现状、需要什么条件）。
    - 判据：读者看完能自己回答"要发生什么事才会亏""这些事可能吗"。只给一个结果数，等于没说原委。
20. **用部分说明整体时，先说这部分有多大代表性。**（2026-09-22 立，研究者要求）
    - 举例用某一类车、某一群车队、某一个项目时，写明它占全体多少（销量占比、车队占比、样本数），并给出全体的加权结果或全部格子；
    - 例子与全体差得多的格子（尤其符号相反的）要点名，不能让例子替全体说话。
    - 判据：删掉这个例子，读者还能不能从文中找到"全体是多少"。找不到，就是以偏概全。

11. **理论在前，跟踪在后**：非共识判断在数据出现之前作出；论证只用本质推理＋已公开信息，要等披露的数据只进跟踪清单（`框架提案.md` §6）。
12. **成对的数必须同源**（2026-09-25 更正；原"两栏各自取证、折扣只许朝不利方向打"作废，它就是不同源拼接）：一个比例、差额或"少活几成"，分子分母必须出自同一家、同一场发布或同一项研究、同一测试口径。**比例可搬，水平不可搬**：比例与水平分开定档，不同来源的两个水平数只作交叉校验，不许拼成一对。用某一时期的新数据，就配同一时期披露的另一侧（`口径/车队总账_换电对充电.md` 第一节）。
    程序检查：情景轴里凡是成对参数，在 `[drivers.*]` 写 `pair_sources`（每档一个信源键），`src/config_loader.py` 加载时检查信源键在台账里、水平固定、三档单调。
13. **反事实基准不得把要检验的变量写死为现状**：否则敏感性测试会把最承重的问题测成不重要（`口径/无换电反事实_制造净利率路径.md`）。
14. **口径写明**：每个外部数登记时写清测量口径（电芯／系统、测试台循环／公里折算、质保／设计寿命、国内／含出口、上险／批发），台账"用于"一栏写它和谁配对。
15. **交叉校验留痕**：定档的数之外，至少找一个不同源的数看量级对不对；对不上先解释（第 2 条），写进关键变量登记表"交叉校验"一栏。
16. **规矩只住一处**（口径文档的合并与拆分另见 `口径/README.md` 二·补）：数据治理规矩住本节；口径文档只写"按本节第 N 条"，不另写一套。发现两处写法不一，以本节为准并当轮删掉另一处。
17. **对手先找最强的那一个**：比较"换电对 X"之前，先列出所有能给同样好处的路，取最强的；早期容易拿下的场景不等于基本盘，增长看网络先铺在哪。
18. **状态文件只写现在**（§1 三分法的执行版）：口径、专题、章、交接、登记表写"现在是什么"；"怎么改过来的""上一版错在哪"只写进 `DECISIONS.md`。文件开头一行"来历"指向 DECISIONS 条目即可。
19. **口径里模型算出来的数一律由程序填**：口径文档写成 `口径/*.src.md`，②类数（模型结果）写占位符 `{{名}}`，`src/caliber_docs.py` 从模型与 `outputs/facts.json` 现算注入 `口径/*.md`（产物，勿手改）；①类输入写键名与取值理由，③类口径取值（如"取中段"）才手写。状态层其他文件（交接、登记表）不抄读数，只写指针。
20. **两道构建闸门**：`python src/build.py` 在最后跑 `caliber_docs`（占位符解析不了 → 失败）与 `state_lint`（口径、专题、章里出现修订标记或"更正／原先／上一版／本轮"等改动叙事 → 失败）。**改完任何参数或文档，跑一次 build，绿了才算改完。**

## 6.1 交互件（沙盘/HTML）的硬规则 —— 以终为始：建立信任

**为什么单列一节：** 2026-09-09 为交互沙盘反复返工一整天，用户最后一句质问是
"我怎么信你呢？"——**这件事值得写进约定，因为它不是代码问题，是目的问题。**

### 目的问题（先于一切技术判断）

交互件不是"把参数摆出来让人拖着玩"，它的**唯一目的**是：

> 让用户在**调整的过程中**验证"程序算的，和我心算的一致"。
> 报告用逻辑建立信任；交互件用**可调、可复现、可对照**建立信任。
> **用户在调整这一步被绊倒，他就不会相信最后那个关键读数。**

由此推出三条不可让渡的准则：

1. **实时反馈**：任何调整——拖滑块、点按钮、输数字——都必须**立刻**反映到读数。
   "要再点一下才看得到"是设计失败。
2. **保持统一**：数值、滑块位置、档位高亮是同一件事的三种表达，**必须同源同刻**。
   三者只要有一个不动，用户的第一反应是"那我到底调对了没有"，信任当场归零。
3. **先看到、再确认**：`预览` = 写入并可继续微调；`应用` = 只做确认。
   绝不允许"必须点了应用才看得到效果"，也绝不允许"应用"覆盖用户在预览后的手动微调。

### 实现准则（第 2 条的技术落法）

| 准则 | 说明 |
|---|---|
| **单一真相** | 一个可调量只能有一处状态。轴的状态只有"偏移 δ"一处，成员值一律**现推**，绝不另存一份 |
| **刷新必须回写三处** | 凡"程序能改、用户也能改"的状态，刷新函数必须同时回写：**滑块位置 + 数值文本 + 档位高亮** |
| **三档不是边界** | 悲观/中性/乐观是**判断参考点**，不是滑块的上下界。硬边界只有一个：`[floor, cap]`，由配置声明——**floor 不一定是 0、cap 不一定是 1**（占有率/份额/渗透率这类恰为 0/1，其余按各自量纲声明）。拿档位当边界 = 拖到底也出不去 |
| **偏移量化到步长倍数** | 否则出现第三位小数、滑块停不到端点 |
| **单位只有一个定义** | **配置里是什么单位，程序就用什么单位算**——月租就全程月租，需要年租时只在用到的那一行 ×12。**不设"显示单位/模型单位"两套、不靠展示层换算**：两套单位并存，必然在某处漏乘或漏除，且错误会被放大若干倍 |
| **对称区间** | 加减范围由**物理边界**决定并左右对称，不要由各成员不等的档位偏移拼出来 |
| **用户视角布局** | 关键总览卡（如"组合实时试算"）必须贴着它所反映的顶部读数放（**列表上方，而非底部**）；批量操作按钮（如"全选 / 全不选"）用**主色高亮**，一眼能找到，避免用户误以为功能被取消；默认状态与总览读数**同源同刻**——默认全不选时，总览读数就是当前模型真实读数 |
| **模板外置，语言不混写** | 生成产物的 HTML／CSS／JS **一律外置到 `templates/`**，不得写在 Python 源码的字符串里。生成器（如 `src/sandbox.py`）只做：跑模型算基线 → 打包 → 读模板替换占位符 → 写文件。理由：写在 Python 字符串里的 JS/CSS 被 IDE 当普通文本（无高亮／补全／lint，语法错要等浏览器才暴露），且会让"把 HTML 删掉重写，报告结论一个字不变"这条完工标准失效——删 HTML 等于删 Python 的一部分。**判据：改一个按钮的颜色，需不需要碰 `.py` 文件？需要 → 就没拆干净。** 触发点：新建或重构任何产出 HTML 的程序时。验证：全仓 `grep` 生成器源码，无 `<script>`／`<style>` 字面量（详见 `框架提案.md` §3「文件构成」表） |
| **结论在前，维度卡片化（版面也是文案）** | 面向人读的区块不许连排长文：**判断（结论）写在最前**，随后每个维度**各成一张卡片**（沙盘①＝业绩/估值/卡位/ROI/重点 五张卡，卡片数/顺序/措辞全在 `narrative/沙盘结论区.md` 的 `# 结论卡片` 下，`##` 一段一张）。顺序也按"先结论、后证据、再看数站不站得住"排（定量支撑先于定性逻辑）。理由：信息齐全 ≠ 读得下去——六行 bullet 连排时读者必须逐行读完才知道哪段讲哪件事；卡片每张自洽、可跳读。**判据：这一屏能否不逐行读就抓到"结论是什么、有哪几个维度"？** 触发点：新增任何"多维度并列"的内容块时。验证：卡片段只改 MD 即生效，`templates/*.js` 与生成器内无卡片标题字面量（用户 2026-09-11 评原版"一堆文字数字看晕了"） |

| **同源单程（无例外：档位态与自定义态都＝精确值）** | 一键三档停在悲观/中性/乐观时，顶部读数＝一页纸对应档列的**精确实跑值**（同一套 Python `build_model`，`build_data` 预计算 `tierValues` 下发）；**用户拖动/勾选进入自定义态后，顶部读数也必须精确**——浏览器内用 **Pyodide 重跑同一套 `build_model`** 取精确值（离线退回生成快照精确值并提示回跑 `run.py`）。**任何位置都不允许"弹性外推 / ±30% 内可信"**：外推值长得像精确实跑值就是骗，会让调参显得不严肃、难让用户相信。**一页纸「当前（实时）」列＝全套 33 行精确值**（三层分组、内容源 `narrative/一页纸.md`，xlsx 已停产）：停在档上＝该档值、自定义＝Pyodide 精确重跑（与一页纸同源，数值列与解释列一并刷新），无"—"、无"≈"、无外推字样（此前"当前列只有 7/17 行、标≈±30%"是用户批不严肃的根因，已根除）。**注入 `<script>` 必须转义或 base64**：内嵌 `D` / `PY_BOOT` / `MODEL_BUNDLE` 时不得直接把含 `</script>` 可能性的字符串塞进 HTML；必须先 JSON（`ensure_ascii=True`，中文转 `\uXXXX` 纯 ASCII）再 base64，浏览器用 **`TextDecoder("utf-8")`**（`b64utf8()`）真解码后 `JSON.parse()`——**绝不能裸 `atob()`**，否则中文乱码（见 `review-plan_claude_20260907.md` §3.6.1 坑 20）。**同源单程只保证"同一套算法"，不保证"算法实现得对"——recompute 跑通≠结果对**：浏览器内 Pyodide 重跑必须经**数值对账**验收（拨一个已知方向、已知量级的轴，确认顶部读数按预期增减、不复现"面板联动但数字不动/变负"），见 §3.6.1 坑 21 与 `DECISIONS.md`「2026-09-10」 |
| **档位方向＝投资价值方向，成本类反向填＋机械校验（资本结构参数排除）** | 三档是"投资价值"的三档：成本类 driver（如谷电单价）须**反向填**——乐观＝低成本、悲观＝高成本。`onepager.check_tier_direction` 每次 `run.py` 校验"乐观档使锚点 `val.swap_increment` 上升、悲观档下降"，违反打印 ⚠ 清单——把"记得小心档位方向"变成机械可判。**但资本结构参数（债/股比）不是经营价值驱动**：`debt_ratio`/`construction_ownership` 标 `structure=true`，跳过该方向校验——因本模型项目权益价值＝EV−债务，杠杆升高使权益切片变小是**正确代数**（非 bug），"放大"指单位权益撬动网络/ROE（已在 DCF 分支含税盾体现）。`debt_ratio` 方向"反"经 B 路线核清（见 DECISIONS 09-09b/09-09c），不靠反向填档位掩盖 |
| **浏览器端可渲染的事实集（进沙盘的内容不许越界）** | 凡要进沙盘的定性内容（一页纸、后续 chapters），其占位符必须能在 **`facts.build_facts(metric_values)` 装配出的键集**内解析——**禁止引用 `sens.*` 及一切依赖敏感性表／三情景表的键**，浏览器端重跑没有这两张表，取不到会**静默退回旧文本**（比报错更糟，因为看起来是对的）。**叙述层读的是 `facts` 不是 JSON 文件**（`build_facts` 入参是 `read_metrics(snapshot, config)` 的指标值字典，JSON 只是不传参时的兜底）——所以"MD 数值跟着用户实时调整走"不需要经过任何文件，浏览器端 `build_model` → `read_metrics` → `build_facts()` 即得当前 facts。触发点：每次往沙盘接入新的 md。验证：`onepager.check` 第 ③ 项（占位符算不出来即报 key）通过，且其作用域随接入范围同步扩大（详见 `DECISIONS.md`「2026-09-13」） |
| **定性文案外置 MD（沙盘内所有定性描述不在 .py 硬编码）** | 沙盘①顶部结论、②定性逻辑三支柱等的论证文案住 `narrative/沙盘结论区.md`，`{{中文名}}` 占位符由 `src/verdict.py` 的 `build_vals` 算出的 `vals` 填（vals 的**键＝中文名**，与 MD 里写的同名）；`templates/` 只含格式与 DOM，**任何涉及定性描述的内容都不写在需要运算的 `.py` 里**。理由：用户要持续调整措辞/论证层次，若硬编码在程序里，改一句话也要动 Python、且无法独立审阅。触发点：往沙盘加任何定性文字时。验证：全仓 `grep sandbox.py` 无中文长句论证文案（模板字符串）；改文案只改 `narrative/沙盘结论区.md` 后重生成 HTML 即生效 |
| **calc 归原程序、sandbox 只取数** | 沙盘的派生测算（分母营运车总规模、REIT 回笼倍数等）一律住在它本来的计算程序里（`scale.py` / `capital_cycle.py`），`sandbox.py` 只 `import` 这些函数并取结果、不做任何组合计算。理由：派生测算若另立第三居所（如 `sandbox_metrics.py`），必与 `scale.py` / `capital_cycle.py` 重复同一段推导（如营运车分母重算 `_operating_stocks` 的里程→保有量换算），改一处漏一处。**判据：把一个函数加进 sandbox 取数链之前，先问"这段计算在 scale.py / capital_cycle.py / model.py 里是不是已经有一处了？有 → 融回原程序，sandbox 只 import"。** 派生出的读数／占比／倍数在 sandbox 里现推、不另存进配置或中间模块（遵守"派生值现推不另存"） |
| **结论区 ①②③ 同源同刻（任一不动＝信任归零）** | ① 顶部结论、② 定性逻辑三支柱、③ 定量看板必须读**同一份**数值——结论区数值由 `src/verdict.py::build_vals(snap,cfg)` 单一函数算出，生成期对三档复用已有 snapshot 得 `D.tierVals`、基线得 `D.baseVals` 离线兜底，浏览器 `py_boot.recompute` 重跑后一并返回 `vals`；JS 侧 `refreshVerdict()` 在 `render()` 与重跑回调里都调，**JS 不写任何算式**（算式写两遍必然漂移）。**可调 driver（估值倍数、持股、服务费、电池租金、电池价）必须走 `cfg` 现读**，绝不能写死进 HTML——否则拖滑块时 ③ 动、①② 不动，页面里两个数字互相打架。**判据：拖任何一个会改估值的滑块时，①② 结论区数字是否跟着 ③ 一起变？不变 → 没接 live vals。** 触发点：往结论区加任何新数字时。验证：拖"CATL 持股比例""EV-EBITDA 倍数"滑块，①② 区读数实时联动；切三档时 ①② 区与该档 ③ 区精确实跑值一致 |
| **占位符一律写中文名 ＋ 生成期机械校验（2026-09-12 取代「扁平具名」）** | `narrative/` 全目录（含 `一页纸.md`、`沙盘结论区.md`）的占位符只有一种写法：`{{中文名}}`（需要裸数时 `{{中文名:n}}`）。中文名＝`configs/metrics.toml`（模型输出）、`configs/base.toml` 功能段的就地信封（输入参数/阈值，key 为点分路径）与 `[[external_quote]]`（`ext.*` 外部引述）或信源台账（`src.*`）的 `label`；**写程序内部名一律中断**（`inject.lint_names()`，唯一例外 `src.*` 信源——它引的是台账那一行，名字就是台账主键）。**不再有第二份名字表**：结论区原先手写的 `PLACEHOLDER_MAP`（文案侧短名 ↔ 数值侧 key）已删，改由 `lab.resolve()` 按 label 寻址，与一页纸、章共用同一套；`src/verdict.py` 的占位符正则直接取 `inject.TOKEN_RE`（第二捕获组即 `:n` 后缀），JS 渲染正则同形态（`{{名}}` 取 vals 对象的 `text`、`{{名:n}}` 取 `bare`）。生成期 `check_placeholders` 校验"MD 里的中文名 ⊆ 输出字典"，**缺一个即终止生成**（不是静默 `[待补]`）；`build_vals` 的 `vals` 以中文名为键、值为 `{v, text, bare}`，浏览器端因此不必再读一遍 md，也不手写任何单位 |

### 配置准则（让配置能解释界面）

- **一套名字管一件事**：滑块步长统一叫 `step`（轴与单参数同义）；
  微扰幅度是"测量用的尺子"，改名 **`perturb`**——它和 `step` 不是一回事，不能同名。
- **不设第二种段**：可调参数全部进 `[drivers]`（有 target、有三档、参与三情景重跑），
  硬边界直接用 `bounds`，**不再单列 `[param_bounds]`**。
- **不在展示层里藏配置**：早期把轴步长写在 `sandbox.py` 常量里，`base.toml` 看不见，
  于是"配置按乘数写、界面按加减走"对不上，排查了好几轮。**凡是界面上能看到的行为，配置里必须能找到出处。**

### 版面准则：按"人怎么用"排，不按"内容有几种"排（2026-09-15 新增）

交互件的版面顺序应当是**一条说服链**，而不是内容清单：

```
结论 → 什么会推翻它 → 为什么这么想 → 怎么算出来的 → 这一轮改了什么
```

四条硬规则：

1. **除结论外默认折叠，但有异常的模块自动展开并标红。**
   一个永远不会自己叫的页面，等于一张需要人记得去看的清单——而人不会记得。
2. **事件/变更挂在它改动的那个参数旁边，不另开清单。**
   让用户在两个地方对账，等于把生产者该做的对账推给了消费者。
3. **常驻读数条只放 2–3 个数。** 放六个就是第二块仪表盘，反而看不清。
4. **"这一轮改了什么"只放程序自己记的读数，不放人写的说明。**
   说明每轮变长，读数表长度恒定；而且**程序记的数能拆穿写说明的人**。

> 这四条都是事后补的——原版面按"内容有几种"排了六层，其中三层是待做占位，
> 而真正决定判断的东西（事件、实测偏离）一层都没有。
> **判据是：打开这个页面，看不出这一轮改了什么的交付，等于没交付。**

### 交付前必做

**前端异常是静默的**（模板里取一个不存在的字段，整个函数无声失效，Python 侧测试全绿）。
所以：改完 HTML **必须重新生成并在浏览器里点一遍**——三档、复位、每条轴的两端、
可行性验证的"分析→勾选 / 改设值即时联动"整条链。**重点不止"联动"——必须确认勾选/设值后顶部读数与面板按预期方向变化（增对增、减对减），不再出现"面板动了数字不动"或读数变负**；若出现红条报错，**先读报错文本**再判断，不得把报错当联动成功。不能只靠读代码判断。

> **本节即准则本身，执行时只读本节即可，不需要回溯任何出处文档。**
> 具体事故清单另记于 `review-plan_claude_20260907.md` §3.6.1，供事后复盘与训练语料，
> 但**那里的记录不构成本节规则的解释依据**——规则在这里已经说全。
