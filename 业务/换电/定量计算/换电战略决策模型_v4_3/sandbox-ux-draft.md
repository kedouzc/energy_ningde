# 换电沙盘 v4.3 · 交互体验设计草稿（待磨）

> 缘起：用户指出沙盘的"可行性验证"表读不懂、派生列是死数——根因不是某个函数写错，
> 而是**动手前没有先定义"做成什么体验才能让用户信任"**。本文件先打草稿，再一起磨。

---

## 一、目标（一句话）

让用户相信：**系统忠实地执行了我做的每一次调整，并给出一个准确的最终结果。**

信任不来自"数字大"，而来自"我动一下、后果立刻可见、且我能对得上"。

---

## 二、不可让渡的四条纪律（已有，照记）

1. **实时反馈**：任何输入（滑块 / 数字框 / 勾选 / 档位按钮）必须**立刻**反映到
   「关键读数」+「三道门」+ 相关派生列。迟一步 = 信任塌一步。
2. **单一真相**：一个可调量只有一处状态（`S[path]` / `A[i]` / `comboRows[i].v`），
   派生值**现推不另存**；刷新必须回写三处（滑块位置 + 数值文本 + 档位高亮）。
3. **先看到再确认**：预览 = 写入并可继续微调；应用 = 只确认、绝不覆盖微调。
4. **同源单程（档位态＝一页纸精确实跑值，且这一条无例外）**：一键三档停在悲观/中性/乐观时，
   顶部读数必须＝一页纸对应档列的**精确实跑值**（同一套 Python `build_model`，由 `build_data`
   预计算 `tierValues` 下发）。**更重要的是：自定义态（用户拖动/勾选后）顶部读数也必须精确**——
   浏览器内用 **Pyodide 重跑同一套 `build_model`** 得到精确值（与一页纸同源），离线时退回生成快照精确值
   并提示回跑 `run.py`。**任何位置都不出现"弹性外推 / ±30% 内可信"**——那会让调参显得不严肃、
   用户不会信（这是用户 2026-09-09 明确否定的设计）。

## 三、本次已在代码落地的修正（用户点出的问题）

- **A. 派生列变活**：可行性表里「预计读数 / 补目标缺口」原是按触边界算的死数；
  现改为按用户「设值」实时重算。触边界结果降为参考列「边界读数*」。
- **B. 组合实时试算**：表格下方新增实时框，每次改值 / 勾选即显示
  「组合后关键读数 ≈ X（补缺口 Y%；距目标还差 Z）」，不用点按钮才出数。
- **C. 填值即启用**：用户在「设值」填数即自动勾选该项，忠实反映"我设了这个数"。
- **D. 用户视角布局**：① 关键总览卡（组合实时试算）放在离它所反映的顶部读数最近处（**列表上方，而非底部**）；② 批量操作按钮（全选/全不选）用**主色高亮**（`class="pri"`），让用户一眼找到，避免误以为功能被取消；③ 默认状态与总览读数**同源同刻**——默认全不选时，总览读数就是当前模型真实读数。
- **E. 一页纸并入沙盘（并做到同源单程）**：Excel 在 IDE 里不能直接看，两个文件跳读破坏信任链。原「一页纸」的 17 行核心指标＋四列判断（合理量级 / 什么会推翻它 / 外部锚）已嵌入沙盘，放在三道门之后；表内是**三情景精确实跑值**（`build_ctx` 整体重跑，与决策树同源）。**关键修正（本回合）**：过去「一键三档」用弹性外推、一页纸用整体重跑，两套算法导致乐观/悲观对不上（中性碰巧一致掩盖了分叉）。现已改为——停在档上时，顶部读数**直接取**一页纸对应档列的精确实跑值（`tierValues`，同源同一套 `build_model`），**不再外推**；自定义态也由 Pyodide 在浏览器内重跑同一套 `build_model`
   取精确实跑值，离线时显示生成快照精确值（全程不再外推）。一页纸另增「当前（实时）」列（见 F），
   让"你拨完这版、核心结论变多少"一目了然。
- **F. 一页纸「当前（实时）」列＝全套 17 行精确值（不再用弹性插值冒充）**：在「悲观/中性/乐观」三档列之后新增一列，反映"你当前这版模型"的核心读数。规则：停在档上时＝该档精确实跑值（＝对应档列）；进入自定义态＝Pyodide 在浏览器内重跑同一套 `build_model` 得到**全套 17 行精确值**（与一页纸同源），离线时显示生成快照精确值。**全程无外推、无"≈"、无"—"**——原先"当前列只有 7/17 行、还标≈±30%"正是用户批"调参不严肃、难相信"的根因，现已根除。
- **G. 档位方向＝投资价值方向，成本类反向填＋机械校验**：三档是"投资价值"的三档，故**成本类 driver 必须反向填**——乐观＝低成本、悲观＝高成本（谷电单价 `valley_power_price` 已修正：悲观 0.40 / 乐观 0.20）。但"记得小心档位方向"会漏，故加 `onepager.check_tier_direction`：每次 `run.py` 逐条 driver 实测"乐观档是否使锚点 `val.swap_increment` 上升、悲观档下降"，违反者打印 ⚠ 清单（本回合 `check_tier_direction` 抓出 `debt_ratio` 方向"反"；经核：项目权益价值＝EV−债务，杠杆越高、债越多、CATL 权益切片越小是**正确代数**，不是模型 bug——`debt_ratio` 是资本结构参数、非经营价值驱动，已标记 `structure=true` 并排除出档位方向校验，见 DECISIONS 09-09b/09-09c）。**把"记得小心"变成机械可判的检查。**
- **列顺序**：参数 / 当前值 / 可调到(触边界) / 设值 / 预计读数 / 补目标缺口 / 边界读数* / 敏感度。
- **H. 精确重跑引擎本身的正确性（同源单程的"实现正确性"关，本回合补上）**：09-09c 后我误以为 recompute 跑通＝结果对，实际连踩三个"能跑、报错被吞、结果错得离谱"的坑：① JSON 字面量拼装——`recomputeExact` 把 `JSON.stringify(state)` 直接拼进 `recompute({...})`，轴里 `isArray` 布尔（true/false）不是 Python 关键字 → `NameError`，被 `.catch` 静默 → "面板动了数字不动"；改：state 以**字符串**经 `pyodide.globals.set("__state_json")` 传入、Python 内 `json.loads` 解析；② 数组被标量覆盖——JS 把数组型参数（nev_rates）在 `S` 里设成 `0`，运行时 `_set_path` 把 config 整条数组替换成 `0`，`build_model` 做 `[year_index]` 下标 → 崩；改：删该赋值（数组只由轴 `A` 管理），recompute 数组分支改用 `ax["cur"]`（保留原始 list）逐元素位移；③ 标量轴方向反了——标量分支把轴 `lo/hi`（**δ 范围**，非值范围）当成值范围去钳 `base+d`，正向 δ 被钳回基线以下、价值暴跌为负；改：先钳 δ 再 `base+d`、最后 `[0,cap]` 兜底。教训见 DECISIONS「2026-09-10」。**同源单程只保证同一套算法，不保证算法实现得对——recompute 跑通≠结果对。**
- **I. 结论区 ①②③ 同源同刻（本回合补上）**：原 ①② 结论区数字在**生成期**算一次写死进 HTML，拖滑块时只有 ③ 定量看板在动——同一页面两个数字互打，违反"任一不动＝信任归零"。改：① 新建 `src/verdict.py::build_vals(snap,cfg)` 作为结论区数值**唯一算法**，生成期对三档复用已有 snapshot 得 `D.tierVals`、基线得 `D.baseVals` 离线兜底，浏览器 `py_boot.recompute` 重跑后一并返回 `vals`；JS 侧 `refreshVerdict()` 在 `render()` 与重跑回调里都调，**不写任何算式**（算式写两遍必然漂移）。② 估值倍数 / 持股 / 服务费 / 电池租金 / 电池价 这类**可调 driver 走 `cfg` 现读**，绝不写死。③ 占位符一律写**中文名** `{{中文名}}`（与叙述层同一形态、同一条正则 `inject.TOKEN_RE`）：2026-09-10f 先定为扁平具名 `{target_year}`，2026-09-12 改为中文名——写文案的人不该被要求记住程序里这个数叫什么；`vals` 的键＝中文名，浏览器端按同名取值。渲染正则 `/\{\{\s*([^{}:]+?)\s*\}\}/g` 与 Python 侧同形态。④ 生成期 `_check_placeholders` 校验"MD 占位符集合 ⊆ `build_vals` 键集"，缺一个即终止生成（不是静默 `[待补]`）。新增派生（稳态更新 GWh 分池含车端+站内、重卡装车/站内/更新、重卡用户 TOC、全成本 TCO 等）一律回原程序（`capex.py`/`scale.py`/`business.py`/`capital_cycle.py`）并在 `lab.py` 登记 Metric，删掉了第三居所 `sandbox_metrics.py`。详见 DECISIONS「2026-09-10f」与 `review-plan_claude_20260907.md` §3.6.1 坑 23/24。

## 四、还值得磨的开放问题（请你定，再写代码）

### Q1. 顶部「关键读数」要不要随可行性表实时变？
- **现状（已改）**：用户反馈"面板脱节"，故已决 —— **可行性表实时驱动同一套 `S/A` 模型状态**，顶部/面板/三道门随勾选·设值即时联动，不再有"规划态/已应用态"之分。
- 取舍：放弃了"先看到再确认"的二次确认按钮（预览/应用已删），换来"我动一下、全屏立刻跟上"的信任感——用户明确要联动。

### Q2. 单参数表的「应用」按钮要不要也实时读数？
- **已决（和 Q1 统一）**：单参数表和组合表完全统一——同一套列（含勾选框、设值、预计读数、补目标缺口、边界读数、敏感度）；单参数行默认不勾选，用户勾选后才加入组合试算，改「设值」自动勾选并实时写入面板；已挪到列表**上方**、紧贴顶部读数的「组合实时试算」自然囊括所有已勾选项。删除「应用」按钮，行为和组合表一致。

### Q3. 数字输入框超可行域是否变红？
- **已决：钳制 + 红框提示**。不是只提示不拦，而是模型实际使用钳制后的值，同时输入框变红并在 `title` 显示「已钳制到可行域 X ~ Y」。用户输入的数保留在红框里（看得见自己被边界挡住了），但面板/读数/预计读数都按钳制后的值走。单参数表同样由 `applyRow` 钳制。

### Q4. 「隔离单因」与「组合叠加」口径要说清
- **已决**：已在组合表下方说明里写清 —— 每行「预计读数」是只动这一项的**隔离读数**；「组合实时试算」才是所有已勾选项**叠加后的当前读数**。避免用户以为"每行加起来 = 组合"。

### Q5. 要不要给"心算对照"留出口
- **已决：按"留出口"方向处理**。后续在关键派生处加 tooltip/说明，给出弹性公式 `读数 = 基线 × (1 + 弹性 × 变动率)`，让用户能拿计算器对一遍，确认程序算的和心算对得上。

## 六、怎么定义"用户需求"（本草稿要回答的元问题）

不靠逐条列举，先问三个问题，答案凑齐就是需求：

1. **用户拿这个工具要做什么决定？**（本例：决定"调哪些参数、调到多少，能让关键读数达标"）
2. **他在做决定时，靠什么建立信任？**（本例：每一步调整都能立刻看到后果、且能心算对账）
3. **哪一步他会被绊住、从而不信任？**（本例：派生列是死数、填了没反应、词看不懂）

凡答不上这三个问题的功能，就是"从程序方便出发"而非"从用户出发"——先不要写。
