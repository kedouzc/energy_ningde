# 超换一体站财务模型 — 架构设计文档

## 0. 可扩展交互式企业估值测算工具需求与架构疑问
### 一、项目核心目标
开发一款**可扩展的交互式企业估值测算工具**，先以**宁德时代**作为首个试点项目，最终抽象成一套能适用于各类企业（尤其是从制造业向重资产运营转型的企业）的通用估值解决方案，是要做成标准程序，还是写成skill，还是有其他解决方案呢？

### 二、试点项目背景（宁德时代）
宁德时代正处于从纯电池制造商向"制造+重资产运营"双模式转型的关键阶段，其业务复杂度和估值争议性都极高：
1. **传统动力电池业务**：延伸出超换一体网络和电池银行，计划2028年建成10万座换电站
2. **储能业务**：延伸出自持电站运营、系统集成和电力交易服务
3. **强协同效应**：换电站和用户车辆的动力电池可作为分布式储能资源参与电网调度
4. **估值特殊性**：A/H股存在显著估值倒挂，不同市场对其新商业模式的定价逻辑差异巨大

### 三、工具核心能力要求
#### 1. 双层参数机制
- 专家层：预设所有参数的合理取值范围、联动约束规则和基准值
- 用户层：用户可在专家预设的范围内，根据自己的专业判断和独特数据源进行自定义调整

#### 2. 多维度测算能力
- 分业务线独立估值（制造业务、资产运营业务，2块业务区分不同产品线，包括动力电池、储能电池、电池回收，CVC和研发投入可以作为业务驱动因素）
- 多场景对比（乐观/基准/悲观）
- 盈亏平衡点测算
- 单参数敏感性分析
- 估值结果拆解与归因

#### 3. 自动化数据更新能力
- 对接多源数据源：公司定期报告、竞争对手公告、专业机构（BNEF、IEA等）的行业数据和价格预测
- 由AI Agent自动爬取、整理和初步校验最新数据
- 支持人工审核机制：AI更新的数据必须经过专家确认后才能正式生效

#### 4. 可视化呈现能力
- 以图表形式展示现金流预测、估值结果、敏感性分析等
- 以文字形式清晰解释估值逻辑、关键假设和结论
- 支持交互式操作，实时展示参数变动对结果的影响

#### 5. 可扩展性要求
- 严格的通用引擎与公司特定配置分离
- 未来添加新公司时，只需新增对应的配置包，无需修改核心代码

### 四、核心架构疑问
我希望采用**严格的职责分离架构**，让HTML页面仅负责用户交互和可视化展示，**不内嵌任何复杂的校验逻辑、估值计算公式和硬编码参数**。

现有以下核心问题需要明确：
1. **参数与规则的存储方案**
   - 参数的取值范围、参数之间的联动约束规则、不同场景的系数，应该用哪种文件格式存储？YAML、JSON还是其他格式？
   - 为什么这种格式更适合同时支持人工维护和AI Agent自动读写？
   - Markdown文档在这个体系中应该扮演什么角色？适合存放哪些内容？

2. **估值模型的拆分与存储**
   - 复杂的估值运算逻辑（如DCF折现、分业务线估值、资产折旧计算、现金流预测）应该如何组织？
   - 哪些部分可以做成通用的计算引擎，哪些部分需要做成公司特定的配置？
   - 运算逻辑是否也需要某种形式的文档化，以便于专家审核和维护？

3. **整体系统的文件架构设计**
   - 整套系统应该如何划分文件和文件夹？
   - 交互页面、配置文件、计算引擎、说明文档、AI Agent接口分别应该放在什么位置？
   - 如何设计才能最大限度方便后续的维护、更新和扩展？

4. **AI Agent对接的架构支持**
   - 为了让AI Agent能够自动更新参数和规则，架构上需要做哪些特殊设计？
   - 如何保证AI Agent的自动更新不会破坏系统的稳定性和数据的一致性？
   - 如何实现"AI更新→人工审核→正式生效"的完整流程？

## 1. 设计目标与方案定位

**最终方案**：采用前端ESM模块化 + YAML配置驱动的单页应用架构，所有逻辑跑在浏览器端，不引入Node.js构建工具。

**部署方式**：浏览器 CORS 策略禁止 `file://` 协议加载 ESM 模块和 fetch 本地文件，需要通过 HTTP 服务器运行。在项目根目录执行：
```
python -m http.server 8080
# 或：npx serve .
```
然后浏览器访问 `http://localhost:8080`。

核心设计目标：
- **参数可配置**：所有业务假设集中在YAML配置文件中管理，改一处全局生效
- **计算可复现**：同一组参数输入，任何时间、任何环境输出一致
- **交互可探索**：用户实时调整参数，秒级看到财务影响
- **文档可联动**：Markdown研究报告中的数字随参数调整自动更新
- **零代码扩展**：新增公司只需复制配置模板文件夹，无需修改任何JS代码
- **AI安全可控**：AI只能写入待审核区，参数变更需经过自动校验+人工确认后才能生效

## 4. 配置体系：双层参数 + 场景矩阵

### 4.1 参数存储方案

采用 **YAML 编写 → JSON 运行时** 的双格式方案：

- **YAML**：人工编写和AI审核的源格式（支持注释、diff友好、非程序员可维护）
- **JSON**：浏览器运行时的零依赖格式（`fetch()` + `JSON.parse()` 原生支持，无需引入 js-yaml 等外部库）

### 4.2 `params.yaml` — 参数仓库（专家层）

```yaml
# 参数仓库：所有可调参数集中定义
# 设计原则：只存数据，不做计算；所有数值必须有来源引用

meta:
  company: "宁德时代"
  version: "2026-05-25-v1"
  base_year: 2026

parameters:
  # ── 电芯与 Pack 成本 ──
  cell_cost:
    value: 0.350
    unit: "元/Wh"
    range: [0.20, 0.60]
    step: 0.005
    editable: true
    source: "电池价格口径统一.md §3.2"
    constraints:
      - type: "less_than"
        target: "pack_integration_cost"
        factor: 3.0
        reason: "电芯成本通常低于 Pack 集成成本的 3 倍"

  pack_integration_cost:
    value: 0.100
    unit: "元/Wh"
    range: [0.05, 0.20]
    step: 0.005
    editable: true
    source: "电池价格口径统一.md §3.3"

  # ── 换电站运营参数 ──
  swap_fee:
    value: 0.40
    unit: "元/km（等效）"
    range: [0.25, 0.60]
    step: 0.01
    editable: true
    description: "单次换电服务收费"

  daily_swaps:
    value: 110
    unit: "次/日"
    range: [50, 200]
    step: 5
    editable: true

  # ── 税率与折旧 ──
  vat_rate:
    value: 0.13
    unit: "比例"
    editable: false          # 专家锁定，用户不可调
    source: "中国现行税法"

  cit_rate:
    value: 0.25
    unit: "比例"
    editable: false

  battery_depreciation_years:
    value: 8
    unit: "年"
    range: [5, 10]
    step: 1
    editable: true
```

**双层参数机制实现**：
- **专家层**：params.yaml 定义所有参数的 `range`（取值范围）、`constraints`（联动约束）、`editable`（是否允许用户调整）
- **用户层**：前端 `ui_sliders.js` 根据 params.yaml 动态生成滑块，滑块范围受 `range` 限制，`editable: false` 的参数显示为锁定状态

### 4.3 `company.yaml` — 业务线构成

```yaml
company:
  name: "宁德时代"
  ticker: "300750.SZ / 9868.HK"
  base_year: 2026
  description: "从纯电池制造商向制造+重资产运营双模式转型"

# 业务线：每个业务线独立估值，SOTP 直接加总，不需要权重
business_lines:
  - id: "mfg_power_battery"
    name: "动力电池制造"
    type: "manufacturing"
    params:
      unit_gross_margin: 0.20
      capacity_gwh: 300
      growth_rate: 0.08
      pe_multiple: 15
    source: "公司年报 §业务分部"

  - id: "mfg_energy_storage"
    name: "储能电池制造"
    type: "manufacturing"
    params:
      unit_gross_margin: 0.18
      capacity_gwh: 120
      growth_rate: 0.25
      pe_multiple: 20
    source: "BNEF储能市场展望 2026"

  - id: "op_swap_station"
    name: "换电站运营"
    type: "asset_operation"
    params:
      station_count: 4000
      daily_swaps: 110
      swap_fee: 0.40
      depreciation_years: 8
      irr_target: 0.12
    source: "公司投资者关系公告"

  - id: "op_battery_bank"
    name: "电池银行"
    type: "asset_operation"
    params:
      battery_count: 50000
      lease_fee_monthly: 800
      residual_value_ratio: 0.15
      depreciation_years: 8
    source: "换电业务相变与估值影响.md §3"

  - id: "op_recycling"
    name: "电池回收"
    type: "asset_operation"
    params:
      annual_capacity_ton: 100000
      recovery_rate: 0.95
      metal_price_index: 1.0
    source: "公司ESG报告"

# 业务驱动因素：不产生独立现金流，作为估值乘数因子
value_drivers:
  cvc_and_rd:
    name: "CVC与研发驱动"
    patent_multiplier: 1.05     # 技术溢出效应，对全体业务线估值施加乘数
    rd_expense_ratio: 0.06
    cvc_portfolio_value: 50     # 亿元
    source: "公司年报 §研发投入"

synergies:
  - from: "op_swap_station"       # 来源方（文档用途，不参与计算）
    to: "mfg_power_battery"       # 受益方：估值将被 factor 放大
    type: "demand_pull"
    factor: 1.05                   # 受益方估值直接乘以该因子
    description: "换电站拉动电池需求 → 制造业务估值上浮5%"
    source: "换电业务相变与估值影响.md §4"

  - from: "op_swap_station"
    to: "op_battery_bank"          # 退役电池进入银行，降本 → 银行业务估值上浮
    type: "asset_reuse"
    factor: 1.10                   # 成本降至90% → 估值上浮约10%
    description: "退役电池降低银行资产获取成本 → 银行业务估值上浮10%"
    source: "换电业务相变与估值影响.md §5"
```

**SOTP 分部加总公式**（协同已内化在 adjusted valuation 中，不再单独加总）：

```
企业总估值 = Σ(各业务线 adjusted 估值) × 业务驱动乘数

           = ( V_mfg_power × synergy_factor
             + V_mfg_storage + V_op_station
             + V_op_battery_bank × synergy_factor
             + V_op_recycling )
             × patent_multiplier
```

各业务线贡献占比为**计算结果**而非输入参数：`占比_i = V_adjusted_i / 企业总估值`。```

**engine_orchestrator.js 的分发逻辑**：
- `business_lines` 按 `type` 路由：`manufacturing` → `mfg_profit_engine.js`，`asset_operation` → `asset_op_engine.js`
- `business_lines` 的估值结果直接加总（SOTP，无权重）
- `value_drivers` 在加总后作为乘数因子统一施加

### 4.4 `scenarios.yaml` — 三场景系数矩阵

```yaml
scenarios:
  baseline:
    name: "基准情景"
    multipliers: {}

  optimistic:
    name: "乐观情景"
    description: "换电标准化快速推进，储能需求爆发"
    multipliers:
      cell_cost: 0.85

      pe_multiple_operation: 1.25

  pessimistic:
    name: "悲观情景"
    description: "换电标准化受阻，价格战加剧"
    multipliers:
      cell_cost: 1.25
      daily_swaps: 0.80
      energy_storage_growth: 0.80
      pe_multiple_operation: 0.80

comparison:
  metrics:
    - "total_valuation"
    - "mfg_power_battery.irr"

```

场景对比时，`engine_orchestrator.js` 遍历三组 multipliers，分别执行完整估值流程，结果并排展示。

### 5.1 `config_loader.js` — 配置加载与校验

```javascript
// js/config_loader.js

/**
 * 配置加载器
 * 职责：从 JSON 加载配置 → 校验约束 → 注入默认值 → 返回运行时配置对象
 */

/**
 * 加载公司完整配置
 * @param {string} companyId - 公司标识符，如 "catl"
 * @returns {Promise<Object>} 完整的运行时配置对象
 */
export async function loadCompanyConfig(companyId) {
  // 1. 加载全局默认值
  const global = await fetch('./config/global.json').then(r => r.json());

  // 2. 加载公司特定配置（覆盖全局默认值）
  const company = await fetch(`./config/companies/${companyId}/company.json`).then(r => r.json());
  const params = await fetch(`./config/companies/${companyId}/params.json`).then(r => r.json());
  const scenarios = await fetch(`./config/companies/${companyId}/scenarios.json`).then(r => r.json());
  const tokenMap = await fetch(`./config/companies/${companyId}/token_map.json`).then(r => r.json());

  // 3. 校验参数约束（在 config_loader 中完成，不依赖外部库）
  const errors = validateParams(params);
  if (errors.length > 0) {
    console.error('参数校验失败:', errors);
    return loadFromCache(companyId);  // 回退到上一次有效的配置缓存
  }

  return { global, company, params, scenarios, tokenMap, loadedAt: new Date().toISOString() };
}

/**
 * 校验参数是否满足声明的约束条件
 * @param {Object} params - 参数仓库对象
 * @returns {string[]} 校验错误列表，空数组表示通过
 */
function validateParams(params) {
  const errors = [];

  for (const [key, param] of Object.entries(params.parameters)) {
    // 检查数值范围
    if (param.range && (param.value < param.range[0] || param.value > param.range[1])) {
      errors.push(`${key}: 值 ${param.value} 超出范围 [${param.range[0]}, ${param.range[1]}]`);
    }

    // 检查联动约束
    if (param.constraints) {
      for (const c of param.constraints) {
        if (c.type === 'less_than') {
          const target = params.parameters[c.target];
          if (target && param.value >= target.value * c.factor) {
            errors.push(`${key} vs ${c.target}: ${c.reason}`);
          }
        }
      }
    }
  }

  return errors;
}
```

### 5.2 `engine_orchestrator.js` — 全公司估值编排

```javascript
// js/engine_orchestrator.js

import { MfgProfitEngine } from '../business_engines/mfg_profit_engine.js';
import { AssetOpEngine } from '../business_engines/asset_op_engine.js';

/**
 * 全公司估值编排器
 * 职责：company.yaml → 遍历业务线 → 分发引擎 → 协同调整 → SOTP汇总
 *
 * 三段式计算链（每个 calcBusinessLine 内部）：
 *   操作参数 → [projection] 多年期FCF数组 → [engine_dcf] EV → [engine_valuation] 估值结果
 */

/**
 * 运行完整估值流程
 * SOTP 公式：企业总估值 = Σ(adjusted 业务线估值) × 业务驱动乘数
 * 协同效应直接在受益方(to)估值上施加 factor，不单独加成，避免双重计数
 * @param {Object} config - loadCompanyConfig() 返回的运行时配置
 * @param {string} scenario - 场景名: "baseline" | "optimistic" | "pessimistic"
 * @returns {Object} 完整估值结果
 */
export function runFullValuation(config, scenario = 'baseline') {
  const { company, params, scenarios, global } = config;
  const multipliers = scenarios.scenarios[scenario]?.multipliers || {};
  const adjParams = applyScenario(params, multipliers, company);

  // 1. 逐业务线独立估值（每个引擎内部完成：操作参数→FCF→DCF→估值）
  const blResults = {};
  for (const bl of company.business_lines) {
    blResults[bl.id] = calcBusinessLine(bl, adjParams, global);
  }

  // 2. 应用协同效应到受益方估值
  //    修正：factor 施加于 syn.to（受益方），而非 syn.from（来源方）
  //    协同直接乘在受益方估值上，内化到 adjusted valuation，不分步加成
  const adjResults = applySynergies(company.synergies, blResults);

  // 3. 业务线直接加总（SOTP，无权重，协同已内化）
  const sumOfParts = Object.values(adjResults).reduce((sum, r) => sum + r.valuation, 0);

  // 4. 应用业务驱动乘数（CVC/研发等技术溢出效应）
  const driverMultiplier = company.value_drivers?.cvc_and_rd?.patent_multiplier || 1.0;

  // 5. 最终估值
  const totalValuation = sumOfParts * driverMultiplier;

  // 6. 计算各业务线贡献占比（仅输出，不参与计算）
  const contributions = {};
  for (const [id, r] of Object.entries(adjResults)) {
    contributions[id] = {
      name: company.business_lines.find(bl => bl.id === id)?.name || id,
      valuation: r.valuation,
      share: totalValuation > 0 ? r.valuation / totalValuation : 0
    };
  }

  return {
    by_business_line: adjResults,
    sum_of_parts: sumOfParts,
    driver_multiplier: driverMultiplier,
    total_valuation: totalValuation,
    contributions,
    scenario,
    timestamp: new Date().toISOString()
  };
}

/**
 * 单个业务线计算分发
 * 每个 engine 内部完成三段式：操作参数 → 多年期FCF投影 → DCF折现 → 估值
 */
function calcBusinessLine(bl, params, global) {
  switch (bl.type) {
    case 'manufacturing':
      return new MfgProfitEngine().calculate(bl.params, params, global);
    case 'asset_operation':
      return new AssetOpEngine().calculate(bl.params, params, global);
    default:
      throw new Error(`未知业务线类型: ${bl.type}`);
  }
}

/**
 * 应用场景系数（双阶段匹配）
 * 阶段1：匹配 params.parameters 中的全局参数（cell_cost, daily_swaps 等）
 * 阶段2：匹配 company.business_lines[*].params 中的业务线级参数（pe_multiple 等）
 */
function applyScenario(params, multipliers, company) {
  const result = JSON.parse(JSON.stringify(params));

  // 阶段1：params.parameters 中的参数
  for (const [key, m] of Object.entries(multipliers)) {
    if (result.parameters?.[key]) {
      result.parameters[key].value *= m;
    }
    // 阶段2：company.business_lines[*].params 中的参数
    if (company?.business_lines) {
      for (const bl of company.business_lines) {
        if (bl.params?.[key] !== undefined) {
          bl.params[key] *= m;
        }
      }
    }
  }
  return result;
}

/**
 * 应用协同效应到受益方估值
 * 协同 factor 直接乘在受益方(syn.to)的估值上，不产生单独的加成项
 * 避免了原版的 from/to 反向错误 + 汇总阶段双重计数
 */
function applySynergies(synergies, blResults) {
  const adjusted = {};
  for (const [id, r] of Object.entries(blResults)) {
    adjusted[id] = { ...r, valuation: r.valuation };
  }

  if (!synergies || synergies.length === 0) return adjusted;

  for (const syn of synergies) {
    const beneficiary = adjusted[syn.to];  // 受益方，非来源方
    if (beneficiary) {
      beneficiary.valuation *= syn.factor;
    }
  }

  return adjusted;
}
```

### 5.3 业务引擎内部的三段式计算链

> 这是工具的核心价值层。每个 `calcBusinessLine()` 调用内部不是一步到位，
> 而是执行以下三段式流水线：

```
操作参数（如 daily_swaps=110, station_count=4000）
    ↓  [第1段：营收/成本投影 — business_engines/*.js 内部负责]
分年度营收预测（2026-2035，含增长率衰减）
分年度成本预测（含折旧曲线）
    ↓
分年度 EBITDA / NOPAT
    ↓  [第2段：自由现金流 — 引擎内部从NOPAT→FCF]
FCFF = NOPAT + D&A - CAPEX - ΔWorking Capital
    ↓
多年期 FCF 数组：[fcf_2026, fcf_2027, ..., fcf_2035]
    ↓  [第3段：折现 — engine_dcf.js]
calcDCF({ cashflows: fcf_array, terminal_growth, wacc, forecast_years })
    ↓
EV（企业价值）
    ↓  [估值输出]
返回 { valuation: EV, irr, payback_years, ... }
```

**关键约束**：
- 第1段和第2段在 `business_engines/mfg_profit_engine.js` 和 `asset_op_engine.js` 内部完成，对外只暴露 `calculate(blParams, globalParams, globalCfg)` 接口
- 第3段由 `engine_dcf.js` 提供，是纯函数，不包含任何业务逻辑
- projection 中使用的增长率衰减因子、成本曲线系数等，定义在 `params.yaml` 或 `global.json` 中，不硬编码

### 5.4 通用引擎接口规范

通用引擎（`engines/`）的设计原则：
- 只接收纯数据参数，返回纯数据结果
- 绝不硬编码任何公司名称、业务线名称或具体数值假设
- 每个函数有明确的输入/输出 JSDoc 定义

**`engine_dcf.js` 示例**：

```javascript
/**
 * 通用 DCF 折现引擎
 * @param {Object} params
 * @param {number[]} params.cashflows - 预测期现金流数组
 * @param {number} params.terminal_growth - 永续增长率
 * @param {number} params.wacc - 加权平均资本成本
 * @param {number} params.forecast_years - 明确预测期年数
 * @returns {{ pv_explicit: number, pv_terminal: number, enterprise_value: number }}
 */
export function calcDCF({ cashflows, terminal_growth, wacc, forecast_years }) {
  let pv_explicit = 0;
  for (let t = 0; t < forecast_years; t++) {
    pv_explicit += cashflows[t] / Math.pow(1 + wacc, t + 1);
  }
  const terminal_value = cashflows[forecast_years - 1] * (1 + terminal_growth) / (wacc - terminal_growth);
  const pv_terminal = terminal_value / Math.pow(1 + wacc, forecast_years);
  return { pv_explicit, pv_terminal, enterprise_value: pv_explicit + pv_terminal };
}
```

```javascript
// js/ui_md_linker.js

/**
 * 扫描所有MD文档中的 {{TOKEN}} 占位符，替换为计算结果
 * @param {Object} result   - runFullValuation 的返回值
 * @param {Object} tokenMap - 从 token_map.yaml 加载的映射表
 */
export function renderMdTokens(result, tokenMap) {
  const sections = document.querySelectorAll('.md-section');
  for (const section of sections) {
    let html = section.innerHTML;
    for (const [token, path] of Object.entries(tokenMap)) {
      const value = resolvePath(result, path);
      html = html.replace(new RegExp(`\\{\\{${token}\\}\\}`, 'g'), formatValue(value));
    }
    section.innerHTML = html;
  }
}
```

### 7.1 三层审核机制

### 7.4 稳定性保障设计

| 设计点 | 实现方式 |

| **写隔离** | AI Agent 只能写入 `ai_agent/patches/pending/`，无权直接修改 `config/companies/` |

| **审核日志** | `audit_log.yaml` 记录每一条参数变更的完整生命周期 |

## 需要批判的问题，按严重程度排列

### 🔴 致命缺陷一：协同效应被错误计算，且存在双重计数

看`engine_orchestrator.js`中的`calcSynergies`：

```javascript
// 现有代码
const synergyValue = fromResult.valuation * (syn.factor - 1);
totalValue += synergyValue;
```

这段代码有两个错误叠在一起。

**错误一：from/to方向用反了。** `company.yaml`定义的协同是"换电站运营(`from`) → 动力电池制造(`to`)"，语义是"换电站拉动电池制造利润上浮5%"。受益方是`to`（制造业务），但代码用的是`blResults[syn.from]`（换电站自身的估值）乘以因子。逻辑和语义相反。

**错误二：双重计数。** 协同效应加成额被叠加在`sumOfParts`之上，而`sumOfParts`本身已经包含了制造业务的完整估值。若按正确语义实现，制造业务的估值要么在计算时就应用factor（那协同不再单独加），要么协同单独计算并加总（那制造估值不应包含factor）。两条路不能同时走。

**修复方向：** 明确协同效应的归属规则，选择其中一种实现路径，并在`methodology.md`中写断言。

---

### 🔴 致命缺陷二：整个架构缺少一条核心计算链

现有设计描述了"输入参数"和"输出估值"，但**中间的多年期财务预测引擎完全缺失**。

DCF引擎的接口是：
```javascript
calcDCF({ cashflows, terminal_growth, wacc, forecast_years })
```

它接收`cashflows`数组——但这个数组从哪里来？从当前架构来看，答案是"不知道"。

用户在前端调整"换电站日均换电次数（daily_swaps）"这个操作参数，到DCF引擎接收FCF数组之间，缺少整整一条**运营参数 → 财务三张表预测 → 自由现金流** 的转换链。

这条链的缺失意味着：目前的`MfgProfitEngine`和`AssetOpEngine`实际上无法输出DCF需要的输入，只能做静态的当年利润乘以PE倍数——这不是DCF估值，是市盈率估值伪装成了DCF。

**缺失的模块：**

```
操作参数（daily_swaps, station_count, swap_fee...）
    ↓  [收入预测模块]
分年度收入预测（2026-2035）
    ↓  [成本结构模块]
EBITDA预测
    ↓  [折旧/摊销模块]
EBIT → NOPAT
    ↓  [营运资本&Capex模块]
自由现金流（FCF）数组
    ↓  [engine_dcf.js]
EV（企业价值）
```

这一条链是整个工具的核心价值，不能缺。建议在`business_engines/`里为每类业务型（制造/资产运营）补充一个`projection_engine`，专门完成"操作参数→多年期FCF"这段计算。

---

### 🔴 致命缺陷三：纯浏览器架构的两个隐形炸弹

**炸弹一：相对路径在fetch()中会失效。**

```javascript
// config_loader.js
const global = await fetch('../config/global.json')
```

`fetch()`的相对路径是相对于HTML页面（index.html）所在目录，而不是JS文件所在目录。这段代码在浏览器里会触发404。正确写法应该相对于项目根目录。

**炸弹二："零门槛部署"与ESM+fetch的实际要求矛盾。**

浏览器的CORS策略禁止通过`file://`协议加载ES模块和fetch本地文件。"直接双击index.html"打不开，必须通过HTTP服务器。这不是"零门槛"，需要在README中明确说明（哪怕只是`python -m http.server`）。

---

### 🟠 重要缺陷四：场景系数的键名与参数ID不匹配

`scenarios.yaml`里的multipliers：

```yaml
optimistic:
  multipliers:
    cell_cost: 0.85
    daily_swaps: 1.20
    pe_multiple_operation: 1.25   # ← 这个键在params.yaml里不存在
```

`applyScenario()`的逻辑是`result.parameters[key].value *= m`——当`pe_multiple_operation`在params.yaml里找不到对应键时，这行代码静默失效，不报错，不提示，估值结果悄悄出错。

同时，`pe_multiple`这类估值参数实际上是在`company.yaml`的业务线params里，不在`params.yaml`里，`applyScenario`对它完全无效。场景系数需要能同时作用于两个配置层，但现在只作用于一个。

### 🟠 重要缺陷五：TOKEN_MAP是代码里的硬编码，违反了零代码扩展原则

```javascript
// ui_md_linker.js
const TOKEN_MAP = {
  'STEADY_YEAR': 'result.op_swap_station.steady_year',
  'TOTAL_BATS_STEADY': 'result.op_battery_bank.total_batteries',
  ...

```

新增一家公司时，该公司的MD文档用了新的占位符（比如`{{TOLL_ROAD_IRR}}`），就必须修改`ui_md_linker.js`。这直接破坏了"零代码扩展"的承诺。

修复方案：把TOKEN_MAP放进`company.yaml`或独立的`token_map.yaml`，由config_loader加载后动态注入到渲染层。

---

### 🟡 设计不完整：A/H股估值倒挂分析从需求到架构消失了

项目背景明确提到"A/H股估值倒挂，不同市场定价逻辑差异"，但整套架构里找不到任何对应的设计。这不只是功能缺失，而是一个需要在SOTP框架之外单独建模的结构问题（不同投资人群体、不同流动性折价、不同参照系的估值乘数）。

---

### 🟡 CVC/研发的全局乘数过于粗糙

```yaml
value_drivers:
  cvc_and_rd:
    patent_multiplier: 1.05   # 对全体业务线估值施加乘数
```

把研发和CVC价值作为一个固定的5%全局乘数，施加于全部业务线，是典型的过度简化。研发投入对制造业务的边际递减效应、对新业务的期权价值、对储能的技术壁垒贡献，三者性质完全不同。

更合理的方案是把CVC作为独立估值项（portfolio NAV），把研发影响显式建模为降本曲线斜率的驱动变量，而不是打一个全局折扣/溢价系数。

**协同效应的修正计算：**

```javascript
// 修正版：协同施加于受益方(to)，且不在sumOfParts中重复计算
function calcSynergies(synergies, blResults) {
  const adjustments = {};  // 对各业务线估值的调整量
  
  for (const syn of synergies) {
    const toResult = blResults[syn.to];      // 受益方，不是来源方
    if (!toResult) continue;
    
    // 协同增量 = 受益方估值 × (factor - 1)
    // 同时从受益方基础估值中扣除，避免双重计算
    const increment = toResult.baseValuation * (syn.factor - 1);
    adjustments[syn.to] = (adjustments[syn.to] || 0) + increment;
  }
  
  // 断言：协同总量 ≤ 任一参与方估值的合理上限
  // 这是估值守恒的代码级保证
  return adjustments;
}
```

# 对 Claude 修订方案的批判性回应

楷体对 Claude 的六项批判逐条评估后，同意 5 项、部分同意 1 项，但不同意他提出的 3 项修复方案。以下说明不同意部分的原因。

---

## 不同意一：引入 FastAPI 后端

Claude 建议在项目中新增 `server/` 目录，包含 `main.py`（FastAPI，3个端点）、`yaml_watcher.py`（YAML变动自动生成JSON）和 `patch_validator.py`（AI补丁校验+Dry-Run）。

**不采纳的原因：**

1. **违反零门槛原则**。引入 FastAPI 意味着用户需要安装 Python 3.8+、`pip install fastapi uvicorn pyyaml`，外加理解 ASGI 服务器的运行方式。这与需求中"方便后续维护、更新和扩展"的初心相悖——一个需要 `pip install` 的工具对非技术用户的门槛远高于单纯的浏览器页面。

2. **YAML→JSON 转换不需要自动化**。当前设计中 params 的更新频率是周/月级别（研报发布后才调），手动跑一次 YAML→JSON 转换完全可行。如果一个工具你一个月只用一次转换脚本，就没有必要为此维护一个常驻服务。

3. **补丁校验在前端就能完成**。`config_loader.js` 中已有 `validateParams()`，检查数值范围、联动约束等。AI Agent 生成的补丁同样走这条校验链，不需要一个独立的 Python 校验器。

4. **敏感性计算不需要卸载**。几十个参数做 Tornado 图，在浏览器主线程跑毫秒级完成。引入 Web Worker 或后端计算的复杂度远超收益。

**结论**：在阶段 0-6 全程，一个 HTTP 静态服务器（`python -m http.server`）就是全部"后端"。真正需要后端的时候（如对接实时行情 API、需要数据库持久化），那是 v2 的问题。

---

## 不同意二：拆分 params 为 schema.yaml + values/base|bull|bear.yaml

Claude 建议将 `params.yaml` 拆分为 4 个文件：`schema.yaml`（专家层边界定义，慢变）、`values/base.yaml`（基准值，快变）、`values/bull.yaml` 和 `values/bear.yaml`（场景值，对 base 的 delta）。

**不采纳的原因：**

1. **当前设计已覆盖这个需求**。`params.yaml` 本身就包含专家层（`range`、`constraints`、`editable`）+ 用户层（`value`），而三场景的差异化参数已在 `scenarios.yaml` 的 `multipliers` 中表达（对 base 的系数）。拆成 4 个文件是在已有方案上叠床架屋。

2. **6 个配置文件对编程小白是灾难**。当前 `config/companies/catl/` 下有 4 个文件（company + params + scenarios + token_map），拆成 7 个后，新增公司时需要理解并填写全部文件——每一层抽象都增加出错概率。配置管理的复杂度增长曲线不是线性的。

3. **delta 语义隐含风险**。bull/bear 作为"对 base 的 delta"存储，意味着读场景值需要合并两个文件。这种依赖关系在手动编辑时极易出错（改了一个忘了另一个），特别是当用户不是程序员时。当前的 `scenarios.yaml` 用独立因子表达场景差异化，一步到位、无合并逻辑。

**结论**：不拆。一个 `params.yaml` + 一个 `scenarios.yaml` 的三场景差异化方案已经足够清晰和可维护。

---

## 不同意三：引入 Web Worker 做敏感性计算

Claude 建议新增 `js/sensitivity_worker.js`，将敏感性计算移入 Web Worker 以避免阻塞主线程。

**不采纳的原因：**

1. **计算量级不匹配**。敏感性分析的做法是在滑动条调整后，立即重新计算所有结果并更新图表。参数数量在 10-30 个量级，每次计算在微秒到毫秒级别。Web Worker 的通信开销（序列化/反序列化 + 消息传递）可能比计算本身更耗时。

2. **实时响应必须跑在主线程**。用户拖动滑块时期望的是即时反馈（<16ms 以维持 60fps 的渲染）。把计算丢给 Worker、等回调回来再更新 DOM，反而引入了异步延迟，用户体验更差。

3. **如果真的需要优化**，正确的方向不是 Web Worker，而是增量计算（只重算变更参数影响的部分）和 DOM 批量更新（`requestAnimationFrame`）。这两个优化在当前规模下也不需要——先让 code 跑对，再让 code 跑快。

**结论**：不引入 Web Worker。敏感性计算在当前规模下根本不是瓶颈，引入异步计算反而损害实时交互体验。

## 总结

Claude 的批判在问题识别层面是准确的（协同反向、路径错误、projection 缺失、场景匹配不完整、TOKEN_MAP 硬编码），已全部采纳并修复。但在解决方案层面倾向于"重型化"——引入后端、拆分文件、加 Worker——这些方案对当前需求而言是过度工程化。保持"纯浏览器 + YAML 配置 + ESM 模块"的轻量架构，是更符合"编程小白友好、零门槛维护"这个核心约束的选择。
