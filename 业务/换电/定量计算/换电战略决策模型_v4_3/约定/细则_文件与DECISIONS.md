> 由重构前的《研究项目约定》§0–§3、§5原文照搬，节号保留（其他文件引用的 §x 在这里查）。**与根目录 `研究项目约定.md` 冲突时，以根目录那一页为准。**

## 0. 它和 skill 到底差在哪

| | **skill** | **项目约定（本文件）** |
|---|---|---|
| 是什么 | 一份**检查表／提问链**，AI 做某类任务时读 | 一套**文件与协作的规矩**，项目开工时铺好 |
| 什么时候起作用 | **做那件事的时候**（"现在要给倍数了，读一下"） | **一直起作用**（每次写文件、每次改动都在守它） |
| 决定什么 | **你怎么想**——想的顺序、不许跳的步骤 | **你想过的东西留不留得住** |
| 载体 | `.claude/skills/<name>/SKILL.md`，AI 按需调用 | 仓库里的一份 md ＋ 目录结构 |
| 怎么迁移 | 装一次，到处可用 | **复制到新项目的仓库里** |
| 失效时的症状 | **该想的没想到** | **想到了，但下次找不到了** |

**判据（分不清时用这条）：**

> **一条规矩，如果 AI 不专门读也应该遵守 → 项目约定。**
> **一条规矩，如果只在做某类任务时才需要想起来 → skill。**

- "DECISIONS 只追加" —— 每次写文件都该守，不需要"调用" → **约定**
- "给倍数前先判定资产性质" —— 只在估值时才需要 → **skill**

**为什么必须两样都有**：没有 skill，你会想漏；**没有约定，你会想到了但留不住**——
三个月后同一个坑再踩一遍，因为当初的判断散落在聊天记录和十几份文件里。
**skill 决定认知的质量，约定决定认知的复利。**

## 1. 文件三分法：状态 / 过程 / 产物

一份文件在动手写之前，先定它属于哪一类。**这是本约定的地基，其余全部由它派生。**

| 类型 | 特征 | 怎么写 |
|---|---|---|
| **状态**（现在是什么） | 只有一份，永远最新 | **覆盖**。不带日期版本号 |
| **过程**（怎么变成这样） | 只追加，永不修改已有条目 | **追加** |
| **产物**（算/生成出来的） | 可随时重新生成，删了不心疼 | 程序写；可带日期版本号 |

**判据（最容易判错的是"产物"）：**

> **能不能从「状态」重新生成？**
> 能 → 产物；**不能 → 它其实是状态，只是伪装成产物。孤儿文件全部来自这里。**

**状态层内部还要再分一刀**（这一刀不分，目标态文档必然烂掉）：

| | 回答什么 | 变化速度 |
|---|---|---|
| **目标态** | 要造成什么样 | 很慢 |
| **当前态** | 现在跑到哪了、下一步干什么 | 每轮都改 |

> **目标态文档里不许出现"当前跑出来的数"。** 需要提到某个量，就写它的
> **名字 ＋ 字段名 ＋ 去哪查**，不写它今天等于多少。
> 判据：**改一个参数重跑，这份文件需不需要改？需要 → 那段写错了地方。**

### 再加一个维度：谁读（2026-09-20 新增）

三分法管"怎么存"，这一刀管"怎么写"。**写法跟着读者走。**

| 类别 | 典型文件 | 写法 |
|---|---|---|
| **A · 给人读**（也给新会话读） | 第 0 章与各章正文、每道门／每轮的一页纸、`交接.md`、版本谱系、`口径/` 白话复核件、阶段性工作计划 | **融合改写，不在文末追加**；结论先行；一件事一个家；不写"上一版如何"；改了哪里由 AI **在对话里**逐条说明（对话就是变更说明，文件保持干净）；尽量短 |
| **B · 人写、程序读** | `narrative/*.src.md`；参数试算用的 Excel | 人话正文＋占位符；格式由程序检查，人不用记规则 |
| **C · 给机器读**（AI 与程序；人按需查） | `DECISIONS.md`（人只看顶部索引表）、`src/`、`configs/`、`build/*.json`、`audit/*.json`、AI 的记忆 | AI 自行维护，只追加或程序生成；不要求好读，但要可检索 |

> **判据：这份文件人会不会从头读到尾？会 → A 类，订正必须融进正文。**
> 教训：一份给人读的工作计划被当成过程记录、在文末追加订正表——利于机读，人读不下去。
> **人日常只需读三样**：第 0 章（当前论点与放弃条件）、当前这一轮的一页纸、被改动的章节正文。

### A 类文件的交稿清单：写成常识能读懂的话（2026-09-21 新增）

**由来**：一页纸写得"每个数都对、整体读不懂"，研究者读不出推理主线；同一个意思在对话里用白话讲一遍就清楚了。
**判据：投资靠常识判断生意能不能做。一个结论说不成常识话，要么没想清楚，要么在用术语掩盖没想清楚。**
A 类文件交稿前，AI 逐条过这张清单（靠清单，不靠自觉）：

| # | 规矩 | 怎么验证做到了 |
|---|---|---|
| 1 | **读者是一个聪明但不懂这一行的人**，每句话他都能复述 | AI 交稿前先用三句话复述全文；复述不出来就重写 |
| 2 | **正文按"五问"组织**：问的是什么／答案（一句话）／凭什么（三到五步，每步一句常识＋一个数）／什么情况下我错了／下一步查什么。四道门模板的七节照用，但每节按这个次序写 | 正文里找得到这五样，且答案在最前面 |
| 3 | **详细算式与大表格写在同一文件末尾的"附录"**，不另开文件；正文只写"算式见附录第几条"。谁都能拿计算器逐行核 | 正文每个数都能在附录找到算式 |
| 4 | **术语规则**：商务、财务的一般说法照常用，但第一次出现时说清楚是什么对什么。三条定死：① 不说"承重数"，说**关键变量**；② "覆盖倍数"写全为**EBITDA 对资本开支（按资本成本折成每年要还的钱）的覆盖倍数**；③ 用"乘数"时写明**对谁、在哪个维度上乘** | 正文里没有"承重数"；覆盖倍数与乘数第一次出现处都有这句说明 |
| 5 | **每个数都说"这意味着什么"**，并跟一个常识参照比（存款利率、债券收益、同行报价……） | 正文里没有孤零零的数 |
| 6 | **正文每节最多一张表、最多五行**；再多就进附录 | 数一遍 |
| 7 | **每个结论后跟一句常识检验**：这符不符合一个做生意的人的直觉？不符合，先怀疑自己算错了 | 每个结论后有这一句 |
| 8 | **交稿自检**：研究者只读正文，能答出"结论是什么、凭什么、什么会让它错"。答不出来是 AI 的问题 | 研究者反馈 |
| 9 | **对话回复同样执行**：先结论、后理由；不讲"我改了哪些文件"，讲"算了什么、结果是什么" | — |
| 10 | **每个数第一次出现，说清来历、单位和时间尺度**：观测／推算／设定三选一；"每度""每月""每车"写全（例：不写"包含 48.5 度"，写"513 度的车每月含 24,880 度"）；设定且无出处的数要明说 | 附录有"输入的数从哪来"表，每个输入数都在表里 |
| 11 | **不留只说不算的话**：提出一个威胁或利好（"快充电芯能缩小差距""只会更狠"），必须给出它会让结论变多少；没有数据就明说"没找到数据"，并给出临界值（到什么程度结论会变） | 正文里没有只有定性、没有量级的判断 |
| 12 | **自造的说法不进正文**（如"穿过零的借钱成本"）；每个概念用读者已有的词说一遍，必要时在文首列"本页用到的词" | 研究者读到没卡住 |

> 纪律登记：本清单约束所有 A 类文件；检查时点＝每次交稿前；验证方式＝上表第三列。

## 2. 目录与准入判据

**文件山的定义不是"文件多"，是「不知道一个文件该放哪 / 不知道去哪找」。**
只要每个目录有一句明确的准入判据，文件多不是问题——
报告写完会有八章 ＋ 若干专题，那是正常的；**散在根目录才是文件山**。

### 2.1 根目录只放「纲领」，五份，硬规则

| 文件 | 回答什么 | 类型 |
|---|---|---|
| `README.md` | **一分钟看懂**：这是什么、怎么跑、去哪找 | 状态·导航 |
| `研究项目约定.md` | **工作台**：文件怎么放、怎么协作 | 状态·约定（可复制到新项目） |
| `框架提案.md` | **要造成什么样**（成果复杂时才需要） | 状态·目标态 |
| `交接.md` | **现在到哪了、下一步干什么** | 状态·当前态 |
| `DECISIONS.md` | **为什么变成这样** | 过程·按主题 |

> **判据：一个新文件想进根目录 → 问它是不是"每次开工都要读的纲领"。不是 → 进子目录。**

### 2.2 子目录，每个一句准入判据

```
<项目根>/
├── configs/              参数
├── src/                  程序
├── 口径/                 跨环节的口径与方法论证
├── narrative/
│   ├── chapters/         报告各章
│   └── topics/           报告论证专题
├── audit/                台账
├── outputs/              组装好的最终产品（报告、沙盘、仪表盘、工作簿）
├── build/                机器中间数据（快照、事实包、状态）
└── _archive/             已被取代的
```

| 目录 | 准入判据 |
|---|---|
| `configs/` | 是一个**可调的输入值**，且**带信源**（没有信源的必须显式标"经验假设"） |
| `src/` | 是**计算逻辑**。**唯一引擎**——同一件事不允许有第二处实现 |
| `口径/` | **一个口径/方法问题需要独立论证，且被多处引用。** 它既支撑定量计算，也能推出定性判断 |
| `narrative/chapters/` | 对应骨架表里的一章。**数量固定，不允许中途增加** |
| `narrative/topics/` | 满足任一：**① 两章以上引用；② 更新周期与模型无关；③ 是一条已定决策的完整论证** |
| `audit/` | 是一份**逐条核对**的清单（信源台账、链路审计） |
| `templates/` | 是**输出格式模板**，被 `src/` 引用。**不含任何业务数字与口径判断**——判据同 HTML 边界：把模板删掉重写，报告结论一个字不变 |
| `outputs/` | **能从上面这些重新生成。** 可带日期版本号 |
| `build/` | 机器中间数据，能重新生成 |
| 与 `.src.md` 同目录的 `.md` | 生成稿（章、专题、口径），能重新生成，勿手改 |
| `_archive/` | **职责已被别的文件完整接管**，且**做过覆盖检查**（见 2.4） |

**`口径/` 与 `narrative/topics/` 容易混，它们的读者不同：**

| | 读者 | 写什么 |
|---|---|---|
| `口径/` | 要**核查或复用这套算法**的人（也是未来的你） | 这个数怎么算的、口径为什么这么定、可迁移的方法 |
| `narrative/topics/` | 读报告的**投资人** | 投资论证的片段 |

### 2.2.0 过程文件的主语：谁是主角

两份过程文件**用途不同，主语也不同**。不声明主语，AI 会默认用自己的视角写——
**那是它的自然位置**，因为它写的是自己刚做过的事。

| 文件 | **主语** | 谁主笔 | 用途 | AI 在里面的位置 |
|---|---|---|---|---|
| `DECISIONS.md` | **我们**（共同的决定） | AI 起草，人 review | ① 人回顾判断的转折点 ② **训练个人数字分身的语料** | **人与 AI 的交互过程都要记**——交互本身就是语料，纠错反复尤其是 |
| `研究历史记录.md` | **我**（人） | **AI 每轮主动起草，人在草稿上改** | **人自己的工作日志** | **只作素材与启发出现，用第三人称。AI 必须主动起草**——但**主语是人**，起草时就用人的视角，不要留给人做视角转换 |

**日志的三条写法（`研究历史记录.md` 专用）：**

1. **小节标题写结论，不写事件。**
   ✅「标准可以类比为品牌价值，在未被商业社会定价前不能加」
   ❌「AI 给公式加了个 O，被打掉了」
2. **只记重要变更的背景、过程、结果。**
   AI 的自省、纠错的心理过程、"我错在哪"——**全部归 `DECISIONS.md`，不进日志。**
3. **段首一句定主题**，让三个月后的自己一眼看出这天在想什么。

> **为什么是"AI 主动起草"而不是"AI 不写"**（2026-09-06 修正）：
> 日志的价值在人的判断，但**打字不是判断**。让 AI 每轮主动起一稿、人在上面删改，
> 比人从空白页开始快得多——**协作的分工是"AI 出材料与结构，人出判断与取舍"，
> 不是"谁的文件谁从头写"。**
> 代价是 AI 会把视角写歪，**所以视角要求写进起草规则里，而不是留给人事后转换。**

> **可迁移的一条：任何人机协作产出的文档，都要显式声明主语。**
> 主语不定，产出就会漂向 AI 的视角——它不是故意的，它只是在写自己看得见的那一半。

### 2.2.1 一条贯穿全部纲领文件的纪律：可独立阅读

> 五份纲领文件里，出现的每个专有名词，**要么在所在文件内定义，要么给出"去哪查"的指针**。
> **不允许出现只有作者当时知道的编号或缩写**（`T1`、`P7`、`方案乙` 这类）。

配一张**术语表**放在文件末尾，是最省事的落地方式。

> ⚠️ 写下任何一条纪律时，同时写清三件事：**约束谁（作用域）、什么时候检查（触发点）、
> 怎么验证执行了（可观察的证据）。** 三件缺一件，这条纪律就会在某个角落失效。

### 2.3 两条防堆山的硬规则

**规则一 · 新建文件三问**

> 1. 它是**状态、过程、还是产物**？
> 2. 已有文件里，有没有哪一份的职责涵盖它？**有 → 写进那一份，不新建。**
> 3. 如果新建，它进哪个目录？**答不上来 → 说明目录体系缺一类，先补判据再建文件。**

第 3 问是关键：**它把"这个放哪"从麻烦变成信号**——
答不上来不是你笨，是分类学缺了一格。

**规则二 · 章数固定，专题按判据生长**

`chapters/` 数量固定。需要更多篇幅 → **提为 `topics/` 专题，不是新增章**。
这保证报告结构稳定：**骨架不动，血肉按判据长。**

### 2.4 归档必须先做「覆盖检查」

> ⚠️ **覆盖检查是必要条件，不是充分条件。**
> 充分条件是**接管方本身已经过人的验收**——
> **覆盖检查回答"能不能接管"，验收回答"接住了没有"；前者 AI 能做，后者只有人能做。**
> 少了后者就归档，是把"我认为覆盖了"当成了"确实覆盖了"。

一份文件要进 `_archive/`，先**逐节确认它的每一节，职责现在归谁**。

> **没做覆盖检查就归档 ＝ 丢东西；不归档又留着 ＝ 留一个会误导人的旧真相。**
> 两害相权，先做检查。**检查结果写进 `DECISIONS.md`**（哪节归了谁、哪节没人接、怎么处理）。

早期的"逻辑记录类"文件（写在还没有 `框架提案.md`／`口径/` 之前的那些）
最容易卡在这里——它们通常**大部分已被接管、小部分还没有**。
不检查就归档会丢掉那小部分；而它往往正是当初想得最细的地方。

### 2.5 本项目之外

有些文件属于**同一研究但不属于本子项目**（比如整个研究方向的日志，
它比这个子项目更早、覆盖面更宽）。**不要为了整齐把它们搬进来**——
在 `README.md` 里给一句指针即可。**目录整洁的目的是找得到，不是对称。**

## 3. `DECISIONS.md`：本约定里最值钱的一份

**它记的是研究过程中的所有转折，不只是代码改动。** 四类，每条必须标：

| 类型 | 记什么 |
|---|---|
| **研究判断** | 对研究对象本身的看法变了 ← **最值钱** |
| 建模口径 | 公式／字段／算法变了 |
| 方法论 | 怎么研究的方法变了 |
| 工作方式 | 文件治理、协作方式变了 |

> **建模 bug 谁都会犯，判断错在哪才是研究者本人。**
> 「研究判断」这一类既是最好的语料，也是报告"诚实清单"章的唯一素材来源。

### 条目格式：六栏 ＋ 两个标记

```markdown
## YYYY-MM-DD · 一句话标题                        [类型]

**当时怎么想的**   ← 不是"背景"，是当时脑子里的模型
**触发**           ← 什么事让你发现不对
**查下来**         ← 事实，带数字带出处
**改成什么**       ← 具体到字段/文件/公式
**影响**           ← 哪些结论跟着变了
**我错在哪 · 学到什么**  ← 全文件最值钱的一栏，见下

→skill: <哪个 skill> · <哪一节>
```

**「我错在哪·学到什么」这一栏的写法**（其余五栏是记录，这一栏是资产）：

1. 先说**错在哪一层**——是算错了、想漏了，还是**问错了问题**
2. 再抽出一条**可迁移的判据**，写成"下次遇到 X，先问 Y"的形式
3. 判据要**能判掉具体的错**，不能是"要仔细""要注意"

> **反例**："以后要注意参数来源。"
> **正例**："任何一个'期限/寿命'参数，先问它约束的是**一个资产单元**还是**整门生意**——
> 前者是技术参数，后者是资产类别判定，必须去查法律/合约权利，不能从第三方评估报告里借。"

**`→skill:` 标记的意义：不要让沉淀依赖回忆，让它依赖标记。**
跑通一遍之后写 skill ＝ **把标记过的条目归拢重写**，不是"回忆我学到了什么"。
**内容清单会变，这个机制不会。**

### 三条格式纪律

1. **只追加，永不修改已有条目。** 判断变了就追加一条新的，写明它深化/推翻了哪一条。
   **纠错本身就是最有价值的语料，抹掉它等于抹掉判断的转折点。**
2. **索引表必须始终完整。** 索引是导航件（可从条目重新生成），
   "只追加"不约束它——**一份不全的索引比没有索引更坏。**
3. **每条改动必配一条条目。** git 答"改了什么"，DECISIONS 答"为什么"。

## 5. 版本与留痕

- **留痕用 git，不用复制目录。** 复制目录的留痕是假的——你看得到两个版本，
  **看不到哪一行为什么变**。
- **一个仓库只能有一个 `.git`，不能嵌套。** 诊断：`git status --short`
  （`U`＝未跟踪 `M`＝改过未提交 `A`＝已加待提交，无输出＝干净）。
- **版本号只长在发布产物上**（`outputs/xxx_YYYYMMDD.html`），**不长在源文件上**。
  源目录里出现 `_v2` `_v3` `_final` 就是文件山的开始。
- `.gitignore` 至少：`__pycache__/`、`*.pyc`、`~$*`、`*.tmp`
